## 1. Executive Summary

The state under review is structurally clear and has an unusually extensive test suite. For a log appender whose central promise is a lock-free or non-blocking hot path, two high production risks nevertheless exist: `KafkaProducer.send` is executed directly on the calling logging thread and is, per the Kafka contract, allowed to block; moreover, the self-logging guard only prevents events from the Kafka network thread, but not synchronous Kafka logs on the calling thread. Under broker, metadata, or buffer problems this can delay request, reactor, or other application threads and, with Kafka DEBUG logging enabled, trigger a recursive log loop up to a stack overflow.

The shutdown and lifecycle paths contain further medium risks: repeated `start()` can orphan resources, four producers can take up to 40 seconds to close one after another, close errors remain invisible in the process, and an event already taken from the fallback queue is not reliably counted as lost on forced shutdown. With multiple appender instances, the Resilience4j meters furthermore collide in the shared registry namespace.

**Test verdict:** The tests are broad, highly readable, and cover many failure paths deterministically. For the most important non-functional system property, however, they create false confidence: `MockProducer` does not block and produces no synchronous internal Kafka logs; the self-logging tests simulate only the expected network thread name; the test configuration suppresses Kafka DEBUG logs. The two high hot-path risks therefore remain undetected despite 226 statically counted `@Test` annotations. No tests were executed, so this is explicitly not a green/red verdict on the current build.

**Overall assessment:** 0 critical, 3 high, 6 medium, 2 low. Before deployment as an appender attached directly to the root logger in latency-sensitive or Reactor-based applications, at least the two high production findings and the associated test blind spot should be remediated.

**Remediation (2026-08-28, commits `490d6fb`, `618f5fa`, and `0a1a420`):** All eleven findings are fully fixed (details in the respective **Status** entry). For H-1 the send path was decoupled asynchronously: `producer.send` runs exclusively on one dispatcher worker per topic class; the logging thread hands off to a bounded queue in O(1).

### High

#### H-1 — `KafkaProducer.send` potentially blocks the application thread

- **Type:** Production — Performance / Robustness / Concurrency
- **Location:** `./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:409`, `./src/main/kotlin/eu/inqudium/tabellarium/ResilientMessageSender.kt:189`, `./src/main/kotlin/eu/inqudium/tabellarium/ResilientMessageSender.kt:205`, `./src/main/kotlin/eu/inqudium/tabellarium/TopicClass.kt:62`
- **Symptom and cause:** The entire path from Logback to `producer.send(record, callback)` runs synchronously on the logging caller. The version-exact Kafka 4.2.1 contract allows `send` to wait up to `max.block.ms` for topic metadata or free buffer memory. The class defaults are 200 to 500 ms; `putIfAbsent` allows the operator to set higher values. The circuit breaker acquires its permission before this call but only receives success or failure after the call returns or via the callback. It therefore does not prevent many parallel callers from waiting simultaneously before it opens.
- **Trigger:** Missing or stale metadata with an unreachable cluster, a first send to a topic, or an exhausted producer buffer; particularly relevant when attached directly to the root logger.
- **Impact:** Request, scheduler, or Reactor event-loop threads can stall for up to the configured `max.block.ms` per log event. Under disruption this grows into a latency cascade; the documented "non-blocking" hot-path property then no longer holds.
- **Fix strategy:** Move all producer sends behind a bounded, non-blocking handoff with clear overflow and loss metrics. Alternatively, asynchronous Logback dispatching must be technically enforced and validated as a mandatory operating condition. A strictly validated, small `max.block.ms` reduces the risk but does not replace decoupling.
- **Confidence:** high; the path is direct, and the blocking behavior is explicitly implemented and documented in the local Kafka 4.2.1 source artifact.
- **Status:** Fixed in `490d6fb` and completed in `0a1a420` (2026-08-28). Two-stage: first, the documented `max.block.ms` limit was enforced as a cap per topic class (`ProducerPropertiesBuilder.capMaxBlockMs`, 500 ms or 200 ms for PERFORMANCE; lower operator values win, higher or unparsable ones are clamped and reported as a violation). Then the send path was fully decoupled: `KafkaAppender.append` performs only CPU work (routing, encoding, enrichment) on the caller thread and hands off to a bounded queue in O(1); `producer.send` runs exclusively on one `SendDispatcher` worker per active topic class (isolation analogous to producers and breakers, FIFO per class). Queue overflow never blocks but routes to the fallback with metric reason `queue.full`; on stop, the dispatchers first drain via the still-open producers, and the remainder goes to the fallback with reason `shutdown`, accounted exactly once. The worker carries the reentry guard from H-2, so Kafka's synchronous caller logging (now on the worker) is discarded instead of fed back. Capacity configurable via `<sendQueueCapacity>`; `send.queue.size/.capacity` gauges per class.

#### H-2 — Self-logging protection misses synchronous Kafka logs and allows recursive log loops

- **Type:** Production — Correctness / Robustness / Concurrency
- **Location:** `./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:409`, `./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:420`, `./src/main/kotlin/eu/inqudium/tabellarium/ResilientMessageSender.kt:205`
- **Symptom and cause:** The guard only discards events whose thread name exactly matches the Kafka producer network thread. In the synchronous `doSend` error path, Kafka 4.2.1 logs an `ApiException` at DEBUG before the user callback is invoked. This log is produced on the original application thread and passes the guard. Logback 1.5.38 provides only a no-op reentry guard by default in `UnsynchronizedAppenderBase`. The reentrantly produced Kafka log therefore invokes the same producer path again; the breaker permission of the outer call has not yet been recorded as a failure, because its callback only follows after the log call returns.
- **Trigger:** `org.apache.kafka` is enabled at DEBUG and `KafkaProducer.send` repeatedly hits a synchronous `ApiException` path, for instance during metadata or buffer problems.
- **Impact:** Recursive sends and renewed wait times can hold the caller for a very long time and eventually produce a `StackOverflowError`. A diagnostic configuration with Kafka DEBUG in particular thus exacerbates a broker outage.
- **Fix strategy:** Place a real ThreadLocal-based reentry guard around the complete append path and discard recursive calls in a controlled manner or count them separately. A logger-namespace exclusion for Kafka can provide additional protection but should not replace the internal reentry protection.
- **Confidence:** high; the ordering of the synchronous Kafka DEBUG log and the callback, as well as the no-op reentry guard, were confirmed in the locally resolved sources of the exact versions.
- **Status:** Fixed in `490d6fb` (2026-08-28). ThreadLocal reentry guard around the complete append path in `KafkaAppender.append`; reentrantly produced events are discarded in a controlled manner (same policy as the network-thread guard).

#### H-3 — Hot-path tests create false confidence for blocking and self-logging

- **Type:** Test — Test quality / concealed production risks H-1 and H-2
- **Location:** `./src/test/kotlin/eu/inqudium/tabellarium/KafkaAppenderTest.kt:768`, `./src/test/kotlin/eu/inqudium/tabellarium/KafkaAppenderTest.kt:1145`, `./src/test/kotlin/eu/inqudium/tabellarium/KafkaAppenderTest.kt:1163`, `./src/test/kotlin/eu/inqudium/tabellarium/JoranXmlConfigurationTest.kt:158`, `./src/test/resources/logback-test.xml:23`
- **Symptom and cause:** The self-logging tests construct only events with the expected Kafka network thread name. The concurrent hot-path test uses a synchronized, auto-completing `MockProducer`; it neither waits for metadata nor logs the real synchronous Kafka error path. The only Joran integration with a real producer expects the fallback when the broker is missing, but checks neither caller latency nor recursion. In addition, the global test configuration sets `org.apache.kafka` to WARN.
- **Trigger:** A change or the existing implementation blocks in the real producer or logs reentrantly on the caller, while the mock-based success expectations remain unchanged.
- **Impact:** The suite stays green even though the two most severe production defects are present. Since this concerns the central design promise of a score-5 component path, the test defect itself must be rated high.
- **Fix strategy:** Add a deterministic producer double that blocks in send via latches and logs reentrantly on the same thread. Verify separately: bounded caller latency, no recursive producer use, correct loss/fallback accounting, and breaker state. The test needs no real broker.
- **Mutation thought experiment:** If the producer is replaced by an implementation that blocks `send` permanently or invokes the same logger before the callback, the existing MockProducer and thread-name tests still pass unchanged or never reach the defect path at all.
- **Confidence:** high.
- **Status:** Fixed in `490d6fb` and completed in `0a1a420` (2026-08-28). New test with a producer double that logs reentrantly and synchronously on the caller thread (without the fix it ends in a StackOverflow), plus a guard-release test and the `max.block.ms` cap test matrix. The previously missing latency assertion now exists deterministically: a latch-blocked producer demonstrably holds the dispatcher worker inside send, while `doAppend` must return in < 200 ms; in addition, a class-isolation test (blocked AUDIT send, TECHNICAL keeps flowing) and overflow-to-fallback and shutdown-accounting tests (`SendDispatcherTest` and appender integration tests).

### Medium

#### M-1 — Repeated `start()` orphans the previously built resources

- **Type:** Production — Resource Management / Lifecycle
- **Location:** `./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:219`, `./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:223`, `./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:226`
- **Symptom and cause:** `start()` has no `isStarted` or dedicated CAS guard. A second call resets the stop guard and overwrites pipeline references with a new ProducerRegistry, circuit-breaker registry, and possibly FallbackDispatcher. `UnsynchronizedAppenderBase.start()` itself does not protect against repeated initialization. The old instances are subsequently no longer reachable via `stop()`.
- **Trigger:** A second programmatic `start()` call on the same instance, or an unusual Logback/Spring lifecycle with a double start.
- **Impact:** Producer network threads, buffers, MBeans, and a fallback worker can live on until process exit; metrics can point at the new state while old resources remain active.
- **Fix strategy:** Make `start()` idempotent or implement an explicit restart as an ordered `stop`-then-start with atomic lifecycle state. Add a test that performs two starts and one stop and sees every created resource closed exactly once.
- **Confidence:** high.
- **Status:** Fixed in `490d6fb` (2026-08-28). `start()` is idempotent (`isStarted` guard with a status warning); a test with two starts and one stop was added that verifies exactly one pipeline and the closing of all producers ever created.

#### M-2 — Producer shutdown can take 40 seconds and swallows every close error

- **Type:** Production — Resource Management / Observability
- **Location:** `./src/main/kotlin/eu/inqudium/tabellarium/ProducerRegistry.kt:76`, `./src/main/kotlin/eu/inqudium/tabellarium/ProducerRegistry.kt:86`, `./src/main/kotlin/eu/inqudium/tabellarium/ProducerRegistry.kt:129`, `./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:483`
- **Symptom and cause:** Up to four class-scoped producers are closed strictly one after another, each with a ten-second default timeout. Only afterwards is the FallbackDispatcher terminated. Every exception from a producer close is caught locally and discarded; the KafkaAppender's outer warning path can therefore never see it.
- **Trigger:** Multiple active topic classes with outstanding records or a disrupted broker connection during pod/context shutdown; alternatively, an exception from `producer.close`.
- **Impact:** The close path may take up to 40 seconds for the producers alone. Typical termination grace periods can expire before that, so later producers and the fallback drain are aborted hard. Close errors remain without a status message and without diagnostics.
- **Fix strategy:** Define a single overall budget for all producers and the subsequent drain; close producers in parallel or deadline-based within this budget. Collect all errors after every close has been attempted and report them in aggregate to the KafkaAppender warning path.
- **Confidence:** high.
- **Status:** Fixed in `490d6fb` (2026-08-28). `ProducerRegistry.close()` closes all producers in parallel within an overall budget (closeTimeout plus a join margin) and, after all close attempts, throws an aggregated exception (causes as suppressed) that the KafkaAppender's warning path reports.

#### M-3 — Forced fallback shutdown does not count an already dequeued event as lost

- **Type:** Production — Correctness / Observability
- **Location:** `./src/main/kotlin/eu/inqudium/tabellarium/FallbackDispatcher.kt:196`, `./src/main/kotlin/eu/inqudium/tabellarium/FallbackDispatcher.kt:198`, `./src/main/kotlin/eu/inqudium/tabellarium/FallbackDispatcher.kt:214`, `./src/main/kotlin/eu/inqudium/tabellarium/FallbackDispatcher.kt:224`, `./src/main/kotlin/eu/inqudium/tabellarium/FallbackDispatcher.kt:241`
- **Symptom and cause:** The worker removes an event from the queue before `fallbackAppender.doAppend` runs. On timeout, `close()` interrupts the worker and subsequently counts only events still in the queue. If the currently running append fails or hangs beyond the close, that event is recorded neither as delivered nor as dropped; the exception is likewise swallowed without a counter. Per dispatcher, exactly one in-flight event can thus fall out of the accounting.
- **Trigger:** Shutdown while the fallback appender needs longer than the 200 ms budget in `doAppend` or throws an exception there after the interrupt.
- **Impact:** The drop metric and the final warning underestimate the loss. For audit or error logs, precisely the triggering event can vanish invisibly.
- **Fix strategy:** Explicitly track ownership and outcome of the event currently being processed. On forced termination or an append failure, count it as dropped exactly once; on later success, allow no double counting. The contract must also cover a worker that outlives the close.
- **Confidence:** high.
- **Status:** Fixed in `490d6fb` (2026-08-28). The in-flight event is accounted exactly once via CAS ownership (`inFlight` AtomicReference): on forced shutdown, `close()` counts it as lost; on a `doAppend` exception, the worker does; later success does not lead to double counting.

#### M-4 — Shutdown test masks the in-flight loss from M-3

- **Type:** Test — Test quality / concealed production risk M-3
- **Location:** `./src/test/kotlin/eu/inqudium/tabellarium/FallbackDispatcherTest.kt:205`, `./src/test/kotlin/eu/inqudium/tabellarium/FallbackDispatcherTest.kt:233`, `./src/test/kotlin/eu/inqudium/tabellarium/FallbackDispatcherTest.kt:240`, `./src/test/kotlin/eu/inqudium/tabellarium/FallbackDispatcherTest.kt:248`
- **Symptom and cause:** The test deliberately anchors a `trigger` event already inside `doAppend`, then puts four more events into the queue and merely accepts `droppedEventCount >= 1`. The queue events satisfy the assertion regardless of whether the in-flight trigger event is accounted for. The comment nevertheless concludes from this that no events are silently swallowed.
- **Trigger:** The production implementation continues to lose, or in the future loses, exclusively the event currently being processed.
- **Impact:** The test stays green and confirms a stronger shutdown guarantee than its assertion verifies. It thereby conceals the medium production finding M-3.
- **Fix strategy:** Observe in-flight and queue losses separately and deterministically. Reliably hold the worker inside the trigger append before the close, check the expected exact counter value, and release only after the assertion; additionally, test the success and exception outcomes separately.
- **Mutation thought experiment:** An implementation that removes all in-flight accounting still passes today's test, because at least one of the four queue events is counted.
- **Confidence:** high.
- **Status:** Fixed in `490d6fb` (2026-08-28). The shutdown test anchors the worker with an uninterruptibly blocking appender and checks the exact counter value (in-flight plus queue) as well as the absence of double counting after release; the `doAppend` exception outcome is tested separately.

#### M-5 — Multiple KafkaAppenders collide on Resilience4j meters

- **Type:** Production — Observability / Multi-instance Correctness
- **Location:** `./src/main/kotlin/eu/inqudium/tabellarium/MetricsBindings.kt:62`, `./src/main/kotlin/eu/inqudium/tabellarium/MetricsBindings.kt:72`, `./src/main/kotlin/eu/inqudium/tabellarium/MetricsBindings.kt:135`, `./src/main/kotlin/eu/inqudium/tabellarium/MetricsBindings.kt:186`
- **Symptom and cause:** The appender's own metrics carry an appender tag, but the bound Resilience4j meters do not. All appenders produce the same breaker names per topic class and each bind their complete registry into the same MeterRegistry. The meter IDs therefore collide. `unbind()` subsequently removes every `resilience4j.circuitbreaker*` meter with these names across the board, even if it is used by another appender instance.
- **Trigger:** Two or more KafkaAppenders in one LoggerContext or process that are bound to the same MeterRegistry.
- **Impact:** State gauges can represent only one instance, counters can be intermixed, and stopping or re-binding one appender removes the observability of the other. Operational decisions are then based on wrong or missing breaker data.
- **Fix strategy:** Make breaker names or binder tags unique per appender and remove only exactly the meter objects registered by this binding. Kafka producer binders should also receive the appender tag so that operator-supplied identical client IDs do not collide.
- **Confidence:** high for Resilience4j; meter identity follows directly from name and tags.
- **Status:** Fixed in `490d6fb` and completed in `618f5fa` (2026-08-28). The breaker metrics are registered by an appender-owned binder that mirrors the metric names and tags of `TaggedCircuitBreakerMetrics` 1:1 and additionally carries the `appender` tag of the other appender meters - the meter IDs are thus unique per instance without breaking the operator API `circuitBreakerName(topicClass)` or existing dashboards. `unbind()` removes exactly the meter objects it registered itself; the event consumers write through per-breaker holders, so re-binds do not stack consumers. The Kafka client meters also carry the `appender` tag (collision protection for operator-supplied identical client.ids). The residual case - two identically named (or unnamed) appenders on the same registry - is reported as a status warning with a recommended action. The optional `resilience4j-micrometer` is no longer needed and was removed from the pom.

#### M-6 — Interrupt during `FallbackDispatcher.close()` is lost and prevents the drain

- **Type:** Production — Concurrency / Resource Management
- **Location:** `./src/main/kotlin/eu/inqudium/tabellarium/FallbackDispatcher.kt:196`, `./src/main/kotlin/eu/inqudium/tabellarium/FallbackDispatcher.kt:211`, `./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:494`
- **Symptom and cause:** Both `Thread.join` calls can throw `InterruptedException`. `FallbackDispatcher.close()` does not catch it; the already-set `closeExecuted` prevents a later retry. The KafkaAppender catches only generically, logs a warning, and continues. The interrupt status has already been cleared by the exception, the queue is neither counted nor drained, and the worker can keep working in parallel with the stopping of the fallback appender.
- **Trigger:** The shutdown/context thread is interrupted during a join, for instance by an expiring container shutdown budget.
- **Impact:** The caller's interrupt protocol is violated; teardown and loss counting remain partial while the worker can still access an already-stopped appender.
- **Fix strategy:** Handle `InterruptedException` explicitly, restore the interrupt status, and perform a safe forced cleanup that does not block again and provides complete accounting. Choose the lifecycle states such that an aborted close is not wrongly considered complete.
- **Confidence:** high.
- **Status:** Fixed in `490d6fb` (2026-08-28). Both joins in `FallbackDispatcher.close()` catch `InterruptedException`, the forced cleanup including in-flight and queue accounting still runs to completion, and the interrupt status is restored before returning.

## 6. Systemic Patterns

### S-1 — The central hot-path promise is mostly verified with semantically too-weak producer doubles

- **Approximate frequency:** eight `MockProducer` constructions in four test classes; one integration with a real producer, but without a latency or reentry assertion.
- **Representative finding:** H-3; associated production consequences H-1 and H-2.
- **Pattern:** The tests are well suited for routing, records, and callback results, but do not model the two properties of the real client that are decisive for operational risk — synchronous waiting and synchronous internal logging.

### S-2 — Time-dependent tests use the real clock and sleep/polling bounds

- **Approximate frequency:** five call sites of the shared `pollUntil` helper plus at least one direct wall-clock latency assertion (`< 200 ms`).
- **Representative location:** `./src/test/kotlin/eu/inqudium/tabellarium/FallbackDispatcherTest.kt:75`.
- **Pattern:** Bounded polling is better than fixed sleeps, but remains scheduler-dependent on busy CI hosts or during long GC pauses. Where possible, latches/barriers should prove events; time limits then serve only as a deadlock safeguard, not as a functional assertion.

### S-3 — Several test comments promise a stronger contract than the assertion demonstrates

- **Approximate frequency:** at least four places: fallback in-flight loss, exact loading of the version resource, mixed ignored Kafka exceptions, and one-time Spring metrics binding.
- **Representative finding:** M-4.
- **Pattern:** The Given/When/Then comments state the right intent, but broad thresholds or indirect observables let relevant mutations stay green. The tests should have, per asserted contract, one directly observable failure state and, for type-based rules, at least one isolated case per type.
