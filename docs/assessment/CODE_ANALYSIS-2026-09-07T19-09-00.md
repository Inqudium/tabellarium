## 1. Executive summary

Tabellarium is in good shape for a component of its kind: the hot path is lock-free as the project convention demands, every asynchronous hand-off is bounded, and the shutdown and worker-death paths use compare-and-set ownership so that every event is accounted exactly once. The four score-5 files (`KafkaAppender`, `SendDispatcher`, `FallbackDispatcher`, `ResilientMessageSender`) contain no deterministic crash, hang, or corruption defect; nothing in this report is Critical. The biggest production risks are all in the *edge* of the design: (a) the metrics conservation `accepted = dispatched + fallback`, which the previous report fixed for encoder failures, is still broken on the most common outage path - Kafka 4.2.1 reports metadata timeouts, buffer exhaustion and record-too-large *synchronously through the callback*, and the sender then counts the same event as both dispatched and diverted; (b) the fallback dispatcher's documented 5 s drain budget is effectively 200 ms, because the interrupt it sends after the graceful wait also aborts the drain; (c) a programmatic `stop()`/`start()` cycle silently loses the fallback appender; and (d) under a slow-but-reachable broker the producer's callback closures retain the full `ILoggingEvent` graph plus a payload copy for every buffered record, so heap use is bounded by `buffer.memory` in payload bytes, not in event size. A notable cluster is *lifecycle asymmetry*: things done on start/bind (fallback slot, metrics, one-shot error guard) are torn down on stop but not restored on restart or after a Logback reconfiguration. The Low findings are robustness and observability edges (metrics unbound before the teardown they should observe, a bind-versus-stop race, an idempotence check that omits `acks`, an unguarded fallback worker thread).

**Test verdict.** *Reliability as a safety net:* high for the risk paths that are structurally testable - latch-anchored blocking, real 8-thread and 16-thread contention, CAS ownership at shutdown and worker death are all pinned deterministically, and the suite would go red for most deliberate mutations of the dispatchers. It lies in one place that matters: the appender-level "exactly once when a pinned send fails after stop" test cannot fail if the claim wiring regresses, because the fallback dispatcher is already closed when the late failure arrives (finding 1); the dispatcher-level primitive is pinned, the appender wiring is not. Two shutdown/accounting tests use `>=` where exact counts are achievable, and two tests have no assertion. Two risk paths are *structurally* untestable today: `MockProducer` never delivers an error through a synchronous callback, and the shutdown budgets use non-injected wall-clock time, so the 200 ms drain defect can only be shown with real waits. *Test pyramid:* healthy and unit-heavy - 261 test methods (grep of `@Test`/`@FuzzTest`), 256 in the default run, one real-broker Testcontainers test in its own CI job, four external-contract characterization tests behind a profile, three Jazzer targets whose regression mode currently runs only the empty input (no checked-in corpus). *Most significant gaps and anomalies:*
- No test drives the synchronous-callback error path of `KafkaProducer.doSend` (finding 2) - the JoranXml end-to-end test hits it with a real producer but asserts no metrics.
- No test drains a fallback queue that needs more than 200 ms but less than the 5 s budget (finding 3); no `stop()` → `start()` restart test (finding 4).
- 29 of 58 appender-starting test bodies never `stop()` the appender; the sender tests never close their dispatcher/registry (pattern P1) - daemon threads, so no hang, but a growing thread population inside one Surefire JVM.
- 38 `pollUntil` sites and three `< 200 ms` assertions remain wall-clock bound (pattern P2, known from earlier reports; bounded and anchored, so tolerated).

### 🟠 High

- [x] 1. [`./src/test/kotlin/eu/inqudium/tabellarium/KafkaAppenderTest.kt:1682`] {High} {Confidence: high} {test quality} The appender-level "exactly once when a pinned send fails after stop" test is green regardless of whether the claim guard is wired into the sender
  - Symptom → cause: The test (`:1614-1683`) stops the appender while a send is pinned, asserts one fallback copy, releases the send so it throws, and asserts "still exactly one copy". But `stop()` has already closed the `FallbackDispatcher` (`KafkaAppender.kt:720`) and stopped the `RecordingAppender` (`:737` → `detachAndStopAllAppenders`) before the late failure arrives. Without the wiring `claimDiversion = pending::tryClaimDiversion` (`KafkaAppender.kt:459`), the sender's send-error path would call `fallbackDispatcher.enqueue`, which returns `false` on the closed dispatcher and counts a drop; the recorder never sees a second event. Additionally the second assertion runs right after `pollUntil { sendReturned.get() }` (`:1678`), i.e. possibly before the sender's catch block has executed at all. The test's own rationale ("without the shared claim, this scenario produced a duplicate fallback line") therefore cannot be reproduced by the test as written. The primitive itself is correctly pinned at unit level in `./src/test/kotlin/eu/inqudium/tabellarium/SendDispatcherTest.kt:493-555` via `lateClaim`; what stays unpinned is the *appender wiring*, whose loss would duplicate fallback lines in production during the interrupt-grace window (the fallback dispatcher stays open there until the registry has closed, up to 10 s later).
  - Triggering condition: any regression that drops or defaults the `claimDiversion` argument in `buildPipeline`; the test stays green.
  - Impact: false confidence at a score-5 spot (duplicate delivery of possibly audit-grade records into the fallback file, double `send.error` fallback counts).
  - Fix strategy: keep the fallback dispatcher alive across the late failure (e.g. observe through a probe that survives `stop()`, or assert on a bound metrics registry's `send.error` counter and on the diversion claim state instead of the closed recorder), and wait for the sender's catch path (not just `sendReturned`) before asserting.
  - **Status:** Fixed in `1c8b048` (2026-09-07). The test now binds a `SimpleMeterRegistry`, captures the `send.error`/`shutdown` fallback counters and the `send.duration{outcome=error}` timer before `stop()` (the sender keeps its Micrometer implementation; the meter objects count on after `stop()` removed them from the registry), captures the send worker thread inside the producer double and **joins** it after releasing the pinned send - so the sender's error path has provably completed before the assertion that no `send.error` fallback was recorded while the late failure itself was (`send.duration` error count 1). Mutation check: with `claimDiversion = { true }` the test fails with `expected: 0.0 but was: 1.0`.

[`./src/main/kotlin/eu/inqudium/tabellarium/ResilientMessageSender.kt:239`] {Medium} {Confidence: high} {correctness / observability} `eventDispatched` is counted for sends that Kafka rejected synchronously through the callback, breaking `accepted = dispatched + fallback` on the primary outage path
  - Symptom → cause: `producer.send(record, callback)` (`:221`) is followed unconditionally by `m.eventDispatched(topicClass)` (`:239`) "after the call returns". In kafka-clients 4.2.1, `KafkaProducer.doSend` catches `ApiException` - which includes `TimeoutException` from `waitOnMetadata` (metadata unavailable for `max.block.ms`, the standard broker-outage symptom), `BufferExhaustedException`, `RecordTooLargeException`, `InvalidTopicException` - invokes the callback **synchronously on the calling thread** with the exception and returns a failed future *without throwing* (verified in the 4.2.1 sources). - [x] 3. [`./src/main/kotlin/eu/inqudium/tabellarium/FallbackDispatcher.kt:235`] {Medium} {Confidence: high} {robustness / data loss at shutdown} The fallback dispatcher's effective drain budget is 200 ms, not the documented `shutdownTimeoutMs` (5 s): the interrupt sent after the graceful wait aborts the drain
  - Symptom → cause: `close()` waits `GRACEFUL_DRAIN_WAIT_MS = 200` ms (`:223-228`), and if the worker is still alive it interrupts it (`:235`) and only then waits the remaining budget (`:242-248`). But an interrupted worker stops draining: the drain loop (`:300-306`) returns after the current delivery once `isInterrupted` is set, and the poll loop (`:277-287`) exits immediately. So the remaining 4.8 s are spent waiting for at most *one* more `doAppend`; everything still queued is then counted as dropped (`:263-266`). The class KDoc (`:51-54`, "waits up to [shutdownTimeoutMs] milliseconds for it to drain remaining events") and the `GRACEFUL_DRAIN_WAIT_MS` KDoc (`:346-351`, chosen only so the worker "has time to observe running=false") document the opposite intent. The sibling `SendDispatcher.close()` (`SendDispatcher.kt:254-271`) gives its drain the full budget before interrupting - the two dispatchers diverge. Amplifier: at `stop()` the send dispatchers divert their remainders (up to four queues of 1 024) into the single fallback queue of 1 024 (`KafkaAppender.kt:707`), then the registry closes (fast when nothing is pending, e.g. breaker open), then the fallback gets its 200 ms.
  - Triggering condition: only at shutdown, when the fallback appender needs more than ~200 ms for what is queued (large events with stack traces, a slow disk, a network fallback appender, or the shutdown-diversion burst above).
  - Impact: data loss on the last-resort path - the fallback is the operator's declared "loss is unacceptable here" choice - with 96 % of the configured budget unused; the loss is counted, so it is visible but avoidable.
  - Test risk gap: `FallbackDispatcherTest.kt:198-210` drains a fast recorder (completes within 200 ms); no test enqueues work that needs between 200 ms and 5 s. Because the budgets are wall-clock (pattern P3), such a test would itself be timing-based.
  - Fix strategy: give the graceful drain the full `shutdownTimeoutMs` before interrupting (mirroring `SendDispatcher.close`), or make the post-interrupt loop keep draining non-blockingly until the budget expires; align the KDoc; consider sizing the fallback queue relative to the sum of send-queue capacities or documenting the shutdown burst.
  - **Status:** Fixed in `1c8b048` (2026-09-07). `close()` joins the worker for the full `shutdownTimeoutMs` first and only then interrupts, followed by a bounded `INTERRUPT_GRACE_MS` (500 ms) - the same two-phase shape as `SendDispatcher.close()`; `GRACEFUL_DRAIN_WAIT_MS` is gone and the class KDoc states the invariant (the interrupt ends the drain, so it must never come before the budget is used). New test drains 30 events at ~20 ms each (600 ms, far beyond the former 200 ms window) with zero drops; the double-close test now pins the worker non-interruptibly and asserts the exact count. The shutdown burst (send-queue remainders into the single fallback queue) is documented in the appender's lifecycle KDoc.

## 6. Systemic patterns

- **P1 - Test fixtures start workers/producers and never close them.** ~29 of 58 test bodies in `./src/test/kotlin/eu/inqudium/tabellarium/KafkaAppenderTest.kt` start an appender without `stop()`; all 22 senders built by `newSender` in `ResilientMessageSenderTest.kt:125-154` leave their `FallbackDispatcher` worker and `ProducerRegistry` open (the file's only two `close()` calls close a `MockProducer` to provoke a failure); several `SendDispatcherTest` and `FallbackDispatcherTest` cases construct a second `FallbackDispatcher` that is not closed. Counting basis: a script over `@Test` bodies matching `appender.start()` without `.stop()`, plus grep of constructor calls versus `.close()` per file. Workers are daemon threads, so the JVM exits, but each leaked appender holds a dispatcher thread, a fallback worker and a `MockProducer`; the Surefire JVM accumulates a few hundred idle threads across the run, which distorts any thread-count or timing observation and hides genuine leaks. Representative: `KafkaAppenderTest.kt:229-240`, `:1048-1069`; `ResilientMessageSenderTest.kt:176-195`. Remedy: a `try/finally` or `@AfterEach` close in the fixtures.
  - **Status:** Fixed in `1c8b048` (2026-09-07). `KafkaAppenderTest` registers every appender built by `newAppender` and stops them in an `@AfterEach` (idempotent `stop()`); `ResilientMessageSenderTest`'s `SenderContext` is `AutoCloseable` (registry, dispatcher, recorder) and every context is closed after each test; `SendDispatcherTest` closes every fallback dispatcher it created. Nested test classes inherit the outer lifecycle methods, so no per-test edits were needed.
