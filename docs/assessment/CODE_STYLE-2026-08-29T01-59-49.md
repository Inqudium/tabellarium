## 1. Executive Summary

This is the second style audit of the codebase; the first (`./docs/assessment/CODE_STYLE-2026-08-28T19-42-54.md`, 7 findings, all fixed in `3af9614…`) remains untouched history, and **every one of its findings was re-verified as still fixed at this commit** — the shared `pollUntil` helper held, the `!!`-free production code held (0 occurrences), the `require`/`requireNotNull` validation vocabulary held, and the external-contract test still follows the house conventions it was aligned to. Since that audit, ten commits touched Kotlin sources (async test-architecture migration, a new real-broker integration test, removal of the all-open plugin, comment-audit remediation), and the question for this round is whether the new code kept the voice. The answer is: **almost completely**. The suite remains remarkably uniform — all 253 default-run test names are backticked `should …` sentences, 252 of 253 tests carry Given/When/Then markers, the assertion style (`isTrue()` call form, AssertJ throughout) is unbroken, expression-body discipline is total (zero single-`return` block bodies in the whole tree), every `var` in production is either Joran-bound, `@Volatile` state, or minimal loop-local state, and the newly required manual `open` (post-all-open) is applied consistently and with rationale comments. What this round finds is edge polish in exactly the places that changed or were never deeply ranked before: the new integration test skipped the documented three-question rationale block, one pre-existing class validates after computing dependent state against the house's validate-first pattern, two inline-FQN stragglers survived the round-1 cleanup, and two single-occurrence consistency nits in the test suite. ### 🟡 Medium

- [x] 1. [`./src/test/kotlin/eu/inqudium/tabellarium/KafkaBrokerIntegrationTest.kt:47`] {Medium} {Confidence: medium} {Test style} The suite's only real-broker test lacks the documented three-question rationale block
  - Actual pattern: the single `@Test` method carries Given/When/Then markers and the class carries an extensive KDoc (why the test exists, why it is tagged and excluded), but the test method itself has no "What is to be tested? / How will the test case be deemed successful and why? / Why is it important…" block.
  - Reference: documented convention (`./CONTRIBUTING.md`: "Test comments follow the existing three-question pattern") as lived by the house — 125 blocks across the suite, and every comparably significant end-to-end test (e.g. the Joran round-trip in `./src/test/kotlin/eu/inqudium/tabellarium/JoranXmlConfigurationTest.kt:87` and `:156`) carries one; the broker round-trip is arguably the least trivial test in the repository.
  - Idiomatic alternative: add the three-question block to the test method (the class KDoc already contains most of the raw material); this also feeds the generated test-evidence page, which renders exactly these blocks.
  - Effect: consistency of the test-documentation convention, and completeness of the published test-evidence rationale for the most audit-relevant test. Confidence medium because the convention's "non-trivial" boundary is lived rather than written.
  - **Status:** Fixed in `4c94456` (2026-08-29) — the test method carries the three-question block (broker acceptance as the untestable-offline part is the core of the "how" answer); the generated test-evidence page now renders a rationale for the suite's most audit-relevant test.

- [x] 2. [`./src/main/kotlin/eu/inqudium/tabellarium/HalfOpenThrottle.kt:67`, `:81`, `:83`] {Medium} {Confidence: high} {Consistency / Structure} Constructor validation runs after dependent state is already computed
  - Actual pattern: `minProbeGapNanos` (line 67) and `lastProbeNanos` (line 81 — an initializer that also invokes the injected `nanoTimeSource()`) are property initializers declared *before* the `init { require(!minProbeGap.isNegative) { … } }` block (line 83); Kotlin executes them in declaration order, so the class computes derived state (and performs its first side-effectful clock read) before rejecting invalid input.
  - Reference: dominant house pattern — every other validating class in the module validates first (`./src/main/kotlin/eu/inqudium/tabellarium/TopicRouter.kt:58` `init` is validation-only; `TopicTable.kt:59` and `MessageEnricher.kt:79` run their `require`s at the top of `init` and assign the derived state below them); general standard (validate-arguments-first, *Effective Kotlin*).
  - Idiomatic alternative: move the `require` ahead of the derived-state initialization (init block before the dependent properties, or requires at the top of a single init block that also assigns) so the guard actually guards. No behavioral defect today — a negative gap still ends in the `require` throwing — but the ordering contradicts what the reader of every sibling class has learned.
  - Effect: consistency and readability of the construction contract; removes the "does anything observable happen before validation?" question the current order forces the reader to answer.
  - **Status:** Fixed in `4c94456` (2026-08-29) — the init-block require moved ahead of minProbeGapNanos and lastProbeNanos, with a comment pinning why the ordering matters (initializers run in declaration order); behavior unchanged, HalfOpenThrottleTest green.
