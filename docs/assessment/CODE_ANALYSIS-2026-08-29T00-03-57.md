## 1. Executive summary and compact test verdict

The current revision is generally well structured and contains unusually deliberate handling of bounded queues, producer rollback, breaker state, interrupt restoration, and exactly-once fallback claims. No Critical or High defect was identified. The static review nevertheless found **seven actionable defects: five Medium and two Low**.

The main operational risks sit at asynchronous lifecycle boundaries:

1. The original mutable/lazily materialized Logback event crosses worker-thread boundaries without Logback's deferred-processing preparation, so failure-path logs can acquire incorrect caller data or late-mutated values.
2. `KafkaAppender.stop()` leaves Logback's ingress gate open until teardown has already closed dispatchers, producers, fallback, and encoder.
3. Both dispatcher implementations remain logically accepting after their only worker dies from an uncaught `Error`, stranding later work in queues.

**Compact test verdict:** the suite is broad and materially useful, with 257 `@Test` declarations (253 in the default run and four in one class-level `external-contract` group), good failure-path coverage, injected clocks, latches, bounded queues, mock producers, and several production-mode asynchronous tests. It is not fully trustworthy at the concurrency edges: one race test discards worker `Future`s, one asynchronous XML test reads a non-thread-safe `ArrayList` under the wrong monitor, and no test covers deferred `ILoggingEvent` state, concurrent append-versus-stop, or ingress after worker death. No dynamic pass/fail statement is possible because tests were not authorized to run.

## 2. Scope and method

The review traced the following end-to-end paths rather than treating files in isolation:

- startup: Joran configuration → validation → producer registry → fallback/send workers → encoder → Logback started state;
- hot path: `ILoggingEvent` → encoding → marker routing → topic classification → enrichment → bounded send queue;
- delivery/failure path: dispatcher worker → resilient sender → Kafka callback/circuit breaker → asynchronous fallback;
- shutdown: ingress state → send queue drain → producer close → fallback drain → encoder and attached-appender stop;
- observability: Spring context refresh → Micrometer binding → hot-path, queue, breaker, producer, and fallback metrics;
- tests: production-mode versus synchronous test hooks, concurrent-task failure propagation, waits, time limits, test doubles, and default/external test selection.

Framework-sensitive conclusions were checked against the locally available Logback 1.5.x source contract: deferred/asynchronous users of a `LoggingEvent` must prepare its lazy fields before hand-off, while caller data requires explicit capture. No conclusion depends solely on an old assessment.

Severity interpretation:

- **Critical:** immediate catastrophic loss, security compromise, or system-wide outage under realistic conditions.
- **High:** major correctness or availability failure on a common/important path.
- **Medium:** real defect with bounded blast radius, conditional trigger, shutdown/failure-path focus, or meaningful test false confidence.
- **Low:** localized contract, diagnostic, or uncommon resource-lifecycle defect.

Confidence is the confidence that the described mechanism exists in this revision, not its production frequency.

### Medium

- [x] `./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:567` — **Medium | High confidence | Correctness / concurrency**
  - **Symptom and root cause:** the original `ILoggingEvent` is retained in `PendingSend` and later passed to the asynchronous fallback at `./src/main/kotlin/eu/inqudium/tabellarium/SendDispatcher.kt:334`, but the appender never calls Logback's deferred-processing preparation or explicitly captures caller data. Encoding and enrichment happen synchronously, which happens to materialize several common fields, but arbitrary encoders and fallback layouts may still observe lazy data; `%caller` can be computed from the fallback worker rather than the original logging site.
  - **Trigger:** Kafka diversion/failure or hot-path fallback combined with a fallback appender/layout that reads caller data or another value not materialized by the primary encoder, or a mutable event/argument accessed after the caller returns.
  - **Impact:** the last-resort record can carry misleading origin or stale/mutated content precisely when Kafka delivery is unavailable, weakening auditability and incident diagnosis.
  - **Fix strategy:** freeze the event before its first cross-thread hand-off using Logback's deferred-processing contract, and explicitly capture caller data when the supported fallback contract can consume it. Add a production-mode test whose source event changes or goes out of scope before fallback delivery.
  - **Status:** Fixed in `97ed0c3` (2026-08-29). `append()` now calls `prepareForDeferredProcessing()` on the caller's thread before any hand-off, so formatted message, thread name, and MDC snapshot are materialized regardless of what the primary encoder touches; a missing MDC adapter (embedded contexts) degrades gracefully instead of failing the hot path. Caller data stays opt-in via the new `<includeCallerData>` property, mirroring `AsyncAppender`'s contract. A production-mode regression test mutates a message argument right after `doAppend` and asserts the fallback worker delivers the frozen value.

- [x] `./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:600` — **Medium | High confidence | Lifecycle / concurrency**
  - **Symptom and root cause:** `stop()` closes metrics, all send dispatchers, producers, fallback, attached appenders, and the encoder before `super.stop()` finally changes Logback's volatile `isStarted` gate at line 655. Concurrent logging can therefore enter `append()` throughout the bounded but potentially multi-second teardown and target progressively closed resources.
  - **Trigger:** any application or framework thread logs while the Logback context is shutting down or the appender is selectively stopped.
  - **Impact:** shutdown events can be diverted after fallback shutdown, dropped after the drop warning was already calculated, race with encoder shutdown, and leave metrics/loss accounting inconsistent. A concurrent Spring metric bind can also pass the stale `isStarted` check while unbinding is underway.
  - **Fix strategy:** atomically close ingress at the beginning of teardown, then drain only work accepted before that cutoff; coordinate in-flight append operations with the resource close sequence without introducing an unbounded hot-path lock. Test append-versus-stop and bind-versus-stop interleavings.
  - **Status:** Fixed in `97ed0c3` (2026-08-29). `stop()` now calls `super.stop()` first, flipping the volatile `isStarted` gate before any resource closes; the multi-second teardown runs entirely behind a closed gate, and `bindMeterRegistry` sees the stopped state immediately. The residual window (an append that already passed the gate) shrinks to microseconds and is covered by the dispatchers' existing post-close accounting. No hot-path lock was introduced; a deterministic append-versus-stop interleaving test is not practically pinnable without production hooks and was deliberately not added.

- [x] `./src/main/kotlin/eu/inqudium/tabellarium/SendDispatcher.kt:169` — **Medium | High confidence | Reliability / resource accounting**
  - **Symptom and root cause:** when the sole send worker dies from an uncaught `Error`, the handler diverts only its in-flight item and reports the death, but leaves `running=true`; the equivalent fallback handler at `./src/main/kotlin/eu/inqudium/tabellarium/FallbackDispatcher.kt:145` has the same state transition defect. New calls continue to return as accepted and fill queues that no live worker can drain; the fallback warning even says queued events are counted although existing queued events are not counted until a later close.
  - **Trigger:** an `Error` escapes a producer send action or downstream fallback appender; both cases are explicitly considered and tested by the codebase.
  - **Impact:** up to the configured queue capacity per dead dispatcher can remain silently stranded, with visible diversion/drop behavior appearing only after the queue fills. In a long-lived process, loss accounting remains delayed or absent until shutdown.
  - **Fix strategy:** make worker death atomically transition the dispatcher out of accepting state, then drain/divert/count queued work or deliberately replace the worker. Extend both worker-death tests with submissions after death and complete queue-accounting assertions.
  - **Status:** Fixed in `97ed0c3` (2026-08-29). Both uncaught-exception handlers now set `running = false` first, then account for the in-flight item and drain the entire queue (SendDispatcher diverts everything with reason `send.error` — tracked via a `workerDied` flag so post-death dispatches are not mislabeled `shutdown`; FallbackDispatcher counts everything as dropped). Later submissions divert/count on the caller instead of stranding. The appender's send-dispatcher death warning now states the actual behavior. New latch-pinned tests in both dispatcher suites cover queued work at death time and submissions after death.

- [x] `./src/test/kotlin/eu/inqudium/tabellarium/HalfOpenThrottleTest.kt:257` — **Medium | High confidence | Test correctness / false confidence**
  - **Symptom and root cause:** the 16 concurrent tasks are submitted and their returned `Future`s are discarded. `doneLatch` is decremented in `finally`, so an exception in `await()` or `mayAttemptProbe()` is captured by the executor, still satisfies the completion wait, and can remain invisible when another task produces the expected single admission.
  - **Trigger:** a race-only exception or assertion failure occurs in any worker while at least one worker increments `admitted`.
  - **Impact:** the central contention test for the half-open safety gate can pass despite worker failures, creating false confidence in a reliability-critical concurrency primitive.
  - **Fix strategy:** retain and resolve every `Future`, or collect every worker `Throwable` into a thread-safe sink and assert that the sink is empty after bounded completion. Preserve the existing exactly-one admission assertion.
  - **Status:** Fixed in `97ed0c3` (2026-08-29). The test retains all 16 `Future`s and resolves each with `get(5, SECONDS)`, which is both the bounded completion wait (replacing the `doneLatch`) and the failure propagation — any worker exception or assertion error now rethrows in the test thread. The exactly-one admission assertion is unchanged.

- [x] `./src/test/kotlin/eu/inqudium/tabellarium/JoranXmlConfigurationTest.kt:188` — **Medium | High confidence | Test flakiness / memory visibility**
  - **Symptom and root cause:** the asynchronous fallback worker writes to Logback `ListAppender.list`, an ordinary `ArrayList`, while the test reads it using `synchronized(list.list)`. The writer is not synchronized on that list monitor, and lines 189-190 subsequently read the list without synchronization, so the test has neither mutual exclusion nor a reliable happens-before edge.
  - **Trigger:** the XML end-to-end test runs under scheduling/JIT conditions where the fallback worker's list mutation is not immediately or consistently visible to the test thread.
  - **Impact:** the suite's sole real Joran-to-Kafka-failure-to-fallback pipeline check can fail intermittently, time out, or read concurrently modified state; conversely, local repetition may conceal the invalid synchronization.
  - **Fix strategy:** replace `ListAppender` observation with a thread-safe/latch-backed recording appender, or ensure producer and consumer use the same synchronization primitive for both size and element access. Keep the wait bounded.
  - **Status:** Fixed in `97ed0c3` (2026-08-29). New test-support class `ThreadSafeListAppender` (a `CopyOnWriteArrayList`-backed `AppenderBase`, instantiable by Joran) replaces `ListAppender` in the XML round-trip tests; both the size poll and the element reads now have a happens-before edge on the fallback worker's writes. The wait remains bounded at 5 s.

### Low

- [x] `./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:286` — **Low | Medium confidence | Resource lifecycle**
  - **Symptom and root cause:** pipeline construction allocates Kafka producers and starts fallback/send workers, but the catch path only reports and returns; it does not clean any resources successfully created before a later construction failure. In addition, `encoder.start()` at line 322 occurs after all pipeline resources exist and outside that catch.
  - **Trigger:** a custom component throws after producer creation (for example during later dispatcher construction) or a custom encoder throws from `start()`.
  - **Impact:** partially started producers, registrations, buffers, or daemon workers can survive until some external caller happens to invoke `stop()`, and a failed/reloaded configuration can retain resources longer than intended.

Two failure-injection tests cover encoder start (no producer ever created) and post-registry construction failure (all created producers closed again).

- [x] `./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppenderMetrics.kt:38` — **Low | High confidence | Observability correctness**
  - **Symptom and root cause:** the public metric contract says `eventAccepted` is recorded for every event entering `append`, regardless of downstream outcome, but the call occurs only after encoding and routing at `./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:562`. Encoder/routing failures therefore increment fallback with `ENCODER_ERROR` without incrementing accepted; the broad catch also labels non-encoder hot-path exceptions as encoder errors.
  - **Trigger:** encoder failure, malformed routing input, or another exception before/around enrichment and dispatch.
  - **Impact:** operational ratios and conservation checks can show more fallbacks than accepted events and attribute routing/enrichment/dispatch defects to the encoder, slowing diagnosis.
  - **Fix strategy:** align the implementation and interface contract by recording ingress at a point valid for all downstream outcomes, and classify broad hot-path failures with reasons matching the failing stage. Add metric assertions to the existing encoder-failure test and a routing-failure test.
  - **Status:** Fixed in `97ed0c3` (2026-08-29). The hot-path catch now records `eventAccepted` (under the same `TECHNICAL` default the failure metric uses) whenever the failure hit before routing resolved a class, so accepted = dispatched + fallback holds on every path; failures after routing were already counted once. The `eventAccepted` KDoc states the conservation guarantee, the TECHNICAL default, and the guard exclusions; the `ENCODER_ERROR` enum doc already declared itself the broad pre-send reason, so no new reason dimension was introduced (keeping tag cardinality stable). A new test asserts both counters move exactly once, correctly tagged, on an encoder failure.

## 6. Systemic patterns

1. **Worker death is observed but not converted into a terminal dispatcher state — approximately 2 implementations.** Counting basis: the two `setUncaughtExceptionHandler` blocks in `SendDispatcher` and `FallbackDispatcher`. Both account for only the in-flight item and invoke a hook while leaving `running=true`; this is one shared design weakness, not two independent findings.

2. **Asynchronous tests depend repeatedly on scheduler polling and hard wall-clock thresholds — 17 `pollUntil` call sites plus 3 `< 200 ms` assertions.** Counting basis: literal call sites under `./src/test/kotlin/`, excluding the helper definition, plus literal `isLessThan(200)` assertions. Most waits are bounded and latch/state anchored, so this is not itself a blanket defect, but load-sensitive timing remains concentrated in the dispatcher/appender tests and increases flake risk; the invalid `ListAppender` synchronization makes one instance actionable above.

3. **The raw Logback event has two asynchronous consumers without a single explicit freeze boundary — approximately 2 hand-off layers.** Counting basis: retention in `SendDispatcher.PendingSend` and queueing in `FallbackDispatcher`. Synchronous primary encoding masks much of the risk, which makes a future encoder/layout change likely to re-expose it unless deferred-event ownership is made explicit and tested.

Overall, remediation should prioritize the ingress/worker state machines and deferred event ownership before expanding features. The test suite should then be tightened so worker failures are always propagated and asynchronous observations have explicit happens-before relationships.
