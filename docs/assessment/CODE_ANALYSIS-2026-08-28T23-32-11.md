## 1. Executive Summary

The current state has eliminated both structural main risks of the predecessor report and made this testable: `producer.send` no longer runs on the logging thread but on a `SendDispatcher` worker per topic class behind a bounded queue; a ThreadLocal reentry guard prevents recursive self-sends, and the guard is extended to the worker threads. The shutdown paths account for in-flight events via CAS ownership, producers close in parallel with an aggregated error message, and the metric identities are instance-unique via an `appender` tag. All eleven findings of the predecessor report were verified against the code and are resolved (section 5, regression check).

The new analysis finds no critical and no high defects. Remaining findings concentrate on the just-introduced asynchronous layer: the send dispatchers close **sequentially** on stop and thereby stack their budgets (up to ~6 s before the actual producer close — the same pattern that M-2 of the predecessor report criticized for the producers, an order of magnitude smaller); on forced dispatcher shutdown the in-flight event can land in the fallback **twice** (conservative direction — duplicate instead of loss); a worker dying from an `Error` goes undetected; and the README wording "takes no lock, atomics only" has been stricter than reality since the bounded queue (ReentrantLock in `offer`).

**Test verdict:** The suite has grown substantially (250 static `@Test`, of which 246 in the default run) and covers the former blind spots deterministically: latch-anchored latency assertions against a blocked producer, class isolation, exact in-flight accounting, reentry via a reentrantly logging producer double. Two observations remain: the majority of the suite runs in the test-only **synchronous** send mode, while production dispatches asynchronously — the production default is exercised by a minority of the tests; and the new asynchronous integration tests poll `MockProducer.history()` unsynchronized alongside the sending worker (a flake risk that the suite already solves elsewhere with a synchronizing wrapper).

**Overall assessment:** 0 critical, 0 high, 1 medium, 4 low. No finding argues against use as an appender attached directly to the root logger; the medium finding concerns the tightness of the shutdown time budget, not the correctness of the hot path.

### Medium

#### M-1 — Sequential close of the send dispatchers stacks shutdown budgets

- **Type:** Production — Resource Management / shutdown latency
- **Location:** `./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt` (stop(), loop over `sendDispatchers.values`), `./src/main/kotlin/eu/inqudium/tabellarium/SendDispatcher.kt` (`DEFAULT_DRAIN_TIMEOUT_MS`, `INTERRUPT_GRACE_MS`)
- **Symptom and cause:** `stop()` closes the up to four send dispatchers strictly one after another; each may drain for up to 1,000 ms plus a 500 ms interrupt grace period. The principle from the M-2 fix of the predecessor report — an overall budget instead of stacked individual budgets — was not applied to the new component.
- **Trigger:** Shutdown while several classes have active but blocked sends (broker gone, metadata missing).
- **Impact:** Worst case ≈ 6 s for the dispatchers alone, then up to 10.5 s of parallel producer close and up to 5 s of fallback drain — together ≈ 21.5 s. That fits within the Kubernetes default grace period of 30 s but leaves little room for the rest of the application shutdown; tighter grace periods break.
- **Fix strategy:** Close the dispatchers in parallel or place a shared deadline over all dispatchers (analogous to the parallel producer close); document the budgets together with the producer close timeout.
- **Confidence:** high; budgets and ordering are directly in the code.
- **Status:** Fixed in `bbf83a2` (2026-08-29). `stop()` closes the send dispatchers in parallel (`closeSendDispatchersInParallel`, one closer thread per class) and waits within a shared budget of drain timeout plus margin; interrupts of the stopping thread end the wait early and are restored. The dispatcher share of the shutdown is thus ~1.5–2 s regardless of the number of classes; the docs (§8 of the config guide, defaults table) were updated.

### Low

#### L-1 — Forced dispatcher shutdown can route the in-flight event into the fallback twice

- **Type:** Production — Correctness / Observability (conservative direction)
- **Location:** `./src/main/kotlin/eu/inqudium/tabellarium/SendDispatcher.kt` (`close()` claim of the `inFlight`, `deliver`), `./src/main/kotlin/eu/inqudium/tabellarium/ResilientMessageSender.kt` (its own fallback routing in the error path)
- If the interrupt grace period expires while the worker is still stuck in `producer.send`, `close()` claims the in-flight item and routes it to the fallback with reason `shutdown`. If the worker later unblocks after all (Kafka's `InterruptException`), `ResilientMessageSender` routes **the same** event into the fallback again via its `SEND_ERROR` path — the CAS protocol only protects against duplicate dispatcher diversion, not against the sender-internal routing decision. Result: a duplicate fallback line and a doubled `events.fallback` counter for one event. Duplicate instead of loss is the right error direction for a logging fallback, but the accounting overstates. Fix strategy: pass the ownership token through to the sender, or suppress the sender diversion for an already claimed item.
- **Confidence:** medium-high; the sequence requires a timing window (> 500 ms of non-interruptible send) but is directly derivable from the contracts.
- **Status:** Fixed in `bbf83a2` (2026-08-29). Each `PendingSend` carries a CAS claim (`tryClaimDiversion`) that all diversion paths share: the dispatcher diversions (overflow, shutdown, worker death) and — via the new `claimDiversion` parameter of `ResilientMessageSender.send` — also the sender's throttle, breaker, synchronous, and callback error paths. Whoever wins the claim diverts alone; breaker bookkeeping and the `sendCompleted` metric continue to run independently of it. Regression tests at the dispatcher level (claim contract) and end to end (uninterruptibly parked send that fails after `stop()` → exactly one fallback line).

#### L-2 — A dispatcher worker dying from an `Error` goes undetected

- **Type:** Production — Robustness / Observability
- **Location:** `./src/main/kotlin/eu/inqudium/tabellarium/SendDispatcher.kt` (`deliver` catches only `Exception`), analogously `./src/main/kotlin/eu/inqudium/tabellarium/FallbackDispatcher.kt`
- If the send action throws an `Error` (OOM, linkage), the worker thread dies without a message and without a replacement. The queue fills up, all further events of the class divert with `queue.full` — the loss is visible, but the cause (dead worker instead of slow broker) is not discernible from the metrics. Fix strategy: `Thread.uncaughtExceptionHandler` or a `finally` flag that reports the state once to the status manager; optionally worker respawn.
- **Confidence:** high for the mechanism; low for the probability of occurrence.
- **Status:** Fixed in `bbf83a2` (2026-08-29). Both dispatchers set an `UncaughtExceptionHandler` on their worker: the in-flight item is accounted for exactly once via the claim protocol (SendDispatcher → fallback with `send.error`; FallbackDispatcher → drop counter), after which the new `onWorkerDeath` hook reports the death including its cause to the appender's status manager. Tests present for both dispatchers.

#### L-3 — Documentation promise "takes no lock, atomics only" is stricter than the implementation

- **Type:** Documentation — accuracy of a central promise
- **Location:** `./README.md` (feature bullet and design section), `./docs/index.md`
- Since the asynchronous layer, the hot path contains a `LinkedBlockingQueue.offer`, which briefly takes a `ReentrantLock`. Functionally uncritical — `java.util.concurrent` locks do not pin virtual threads, and the hold time is nanoseconds — but "no lock, atomics only" is thereby literally false; exactly this kind of discrepancy between promise and code was the root of the earlier H-1. Fix strategy: refine the wording to "no blocking, O(1) bounded hand-off" or similar, or switch to a lock-free MPSC queue.
- **Confidence:** high.
- **Status:** Fixed in `bbf83a2` (2026-08-29). README (feature bullet and naming section) and `docs/index.md` now claim "never blocks (no synchronized doAppend, no waits, no I/O)" instead of "takes no lock, atomics only" — the promise thus matches the code exactly (the brief internal lock of the queue's `offer` does not block and does not pin virtual threads).

#### L-4 — Async integration tests read `MockProducer.history()` unsynchronized alongside the worker

- **Type:** Test — harness race / flake risk
- **Location:** `./src/test/kotlin/eu/inqudium/tabellarium/KafkaAppenderTest.kt` (`Asynchronous send dispatch`, `pollUntil { technicalProducer.history().size == 3 }`)
- `MockProducer` is not thread-safe; the dispatcher worker writes to the sent list while the test thread polls `history()` (an unguarded copy). The suite knows this problem and solves it elsewhere with `SynchronizedTestProducerFactory`; the new tests do not use the wrapper. Rare in practice, but an avoidable CI flake risk. Fix strategy: use the same synchronizing wrapper (or a `CountDownLatch` in the send action).
- **Confidence:** high.
- **Status:** Fixed in `bbf83a2` (2026-08-29). `BlockingProducerFactory` now wraps every `MockProducer` (send under `synchronized(mock)`), and the tests read the history exclusively via the synchronized `historySize` helper — the same pattern as the existing `SynchronizedTestProducerFactory`.

## 6. Systemic Patterns

### S-1 — The suite predominantly exercises the test-only synchronous send mode, not the production default

- **Approximate frequency:** The test helper sets `useSynchronousSendForTests = true` as the default; only the `SendDispatcherTest` class (9 tests), three appender integration tests, and the Joran integration run asynchronously — the remaining ~230 tests traverse a path that production never takes.
- **Pattern:** This is the deliberate continuation of the `useSynchronousFallbackForTests` pattern and defensible for determinism, but it inverts the ratio of tested to shipped behavior. Regression risks that only arise in the interplay of queue/worker/metrics (ordering, visibility, shutdown effects) rest solely on the few async tests. A concurrency test that exercises the async path under load from many threads (the analogue of the existing sync hot-path test) is missing.
- **Addressed in `bbf83a2`:** A contention test (8 threads × 250 events) now exercises the production dispatch including queue hand-off and worker drain; the sync default of the rest of the suite remains as a deliberate determinism decision.

### S-2 — Wall-clock latency assertions remain scheduler-dependent

- **Approximate frequency:** three `< 200 ms` assertions (FallbackDispatcher enqueue, SendDispatcher dispatch, appender doAppend) plus the `pollUntil` helpers.
- **Pattern:** The latches anchor the blocked state deterministically — the actual assertion is sound — but the 200 ms bound still measures wall-clock time and can break on pathologically loaded CI hosts. Acceptable as a deadlock safeguard; the bound should not be tightened further.

### S-3 — The synchronous test modes deviate semantically from the production path

- **Approximate frequency:** two places: `FallbackDispatcher.enqueue` (synchronous) swallows `doAppend` exceptions without drop counting, while the worker path counts them; `SendDispatcher.dispatch` (synchronous) checks `synchronous` before `running` and therefore keeps sending even after `close()`.
- **Pattern:** Both deviations are confined to test code and practically inconsequential, but they mean that tests in sync mode observe slightly different bookkeeping than production. Where counter values are the subject of a test, the sync modes should take the same accounting order as the worker paths.
- **Addressed in `bbf83a2`:** Both sync modes now perform the same bookkeeping as the worker paths (drop counting on `doAppend` failures; `running` check before the inline send), each with a test.
