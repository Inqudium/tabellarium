## ⚠️ Discarded first pass (documented per the no-silent-rerun rule)

The first execution of the sender-path and pipeline benchmarks (R2/R5/R6) was **discarded as invalid**: the benchmark JVMs ran without a Logback configuration, so the *default* logging context fell back to root=DEBUG-to-console — and Resilience4j logs a DEBUG line **per breaker call**. Those runs therefore measured Logback string formatting and console appending per operation (15 GB of log output in one run; the classic "measuring the framework" pitfall), inflating the sender path to ~838/2 078 ns and ~2.3/6.1 KB per op. The fix is `./benchmarks/src/main/resources/logback.xml` (root OFF — the appender under test uses its own private `LoggerContext` and is unaffected), the contaminated outputs were deleted, and R2/R5/R6 were re-executed. The clean numbers below differ from the contaminated ones by roughly an order of magnitude — which materially changed the verdict of finding 3 and is exactly why the discard is documented rather than papered over. R1/R3/R4 never had logging on their measured paths and were not affected (verified by output size and content).

## 1. Executive summary

Three findings of `PERF_ANALYSIS-2026-08-29T11-01-08` were measured: **one confirmed (small), one confirmed with its magnitude settled as modest, one retired for the stated load profile with a measured ceiling** — and the session's most consequential result is methodological: the first pass had to be discarded for per-op DEBUG logging contamination (see above), which had inflated the metrics-envelope finding tenfold. Clean results: **finding 2 confirmed with counted-mechanism precision** — the shared-header candidate saves exactly **160.0 B/op** (~23 ns) — a real but small tidy-up; **finding 3 confirmed as modest** — binding metrics costs **+119.8 ns and +210.7 B per delivered event** (SimpleMeterRegistry), which at the assumed 10 k events/s translates to ~2 MB/s of young-gen churn and ~0.1 % of one core: the input report's original "small envelope" estimate was right, and the finding is retired **for action** at realistic rates; **finding 1 retired for the load profile** — the put-lock does serialize under worst-case fan-in (offer mean 173 ns → 8.4 µs from 1 → 32 back-to-back producers, measured ceiling ≈ 4–6 M hand-offs/s per class queue), but the assumed operating point sits two orders of magnitude below that ceiling, and the saturated pipeline sheds visibly instead of stalling callers (p99 0.4 µs single-caller under full saturation). Net: **no optimization is warranted at the stated load profile**; the benchmarks remain as regression assets and re-open instruments. Generalization: relative comparisons and allocation numbers carry to production (with the stated escape-analysis caveat); absolute latencies from this powersave-governed laptop-class machine do not.

## 4. Results per finding

### Finding #1 from PERF_ANALYSIS-2026-08-29T11-01-08 — **Retired for the load profile (mechanism measured, ceiling established)**

- Claim under test: the `LinkedBlockingQueue` put-lock is the sole caller-side synchronization point; contention under high fan-in is unknown and potentially the first silent scaling cost.
- Instrument: JMH asymmetric group (`HandoffBenchmark`): N producers `offer` into a bounded LBQ (2¹⁶) kept near-empty by one batch-draining consumer (`drainTo(…, 4096)`) — the worst-case contention regime, since real callers do encoding work between offers. **Instrument redesign, documented:** the first idea (open-loop `doAppend` through the appender) was invalid for this finding — its path-mix counters showed the majority of events taking the overflow path, on which `offer` rejects via the count check *without touching the lock*. The redesigned benchmark reproduces the production regime (near-empty queue); the `rejected` aux counter proves the regime per run.
- Baseline vs. candidate: scaling curve of the unchanged primitive at 1 / 8 / 32 producers (the input decision rule is threshold-based on the baseline; no candidate implementation was warranted before measurement).
- Decision rule (fixed before the run): retire if offer cost at 32 producers stays below ~1 µs mean; treat as confirmed contention if it escalates into a multi-µs parking regime — then translate to the load profile before recommending anything.
- Result (avgt, mean ± 99.9 % CI; sample p99 in parentheses):
  - 1 producer: **173 ± 17 ns/op** (p99 1.86 µs)
  - 8 producers: **1 558 ± 558 ns/op** (p99 59.2 µs); rejected ≈ 0
  - 32 producers: **8 441 ± 540 ns/op** (p99 353.8 µs); rejected ≈ 0
  - Implied serialized hand-off capacity: 32/8.44 µs ≈ **3.8 M offers/s** at 32 producers (≈ 5.8 M/s single-producer) — the lock's measured ceiling on this machine.
- Fork variance: notable at 8 producers (±36 % CI — scheduler noise under powersave); direction unambiguous in every fork. The 1-producer configuration logged a nonzero `rejected` count (≈ 0.5 % of ops; absent at 8/32) — a consumer-scheduling artefact; it can only inflate the 1-producer baseline and therefore biases *against* this retirement.
- System translation (the deciding step): the assumed profile is ≤ 50 k events/s per instance across all classes — ≈ **1 %** of the measured worst-case ceiling of one class queue; even 10× the profile is ≈ 13 % of a resource whose contended regime additionally requires back-to-back offers with no work between them (production callers pay the encoder between offers). Secondary evidence (clean R6): under full open-loop saturation with shedding engaged, caller-side `doAppend` p99 was **0.4 µs (t 1) / ~35 µs (t 8) / ~250 µs (t 32)** — growth driven by oversubscription and the saturated regime, still far from caller-stalling territory, and production operates nowhere near this regime.
- Verdict: **retired for the stated load profile** — `Effect: measured`; no action below per-class rates approaching ~10⁶ events/s. The measured ceiling is the number future capacity discussions should cite; re-open via this benchmark if a host approaches it (an MPSC hand-off would then be the candidate).
- Change cost: n/a (no change recommended).
- Raw output: `./benchmarks/results/2026-08-29/r3-handoff-p{1,8,32}.txt`, `r4-handoff-sample-p{1,8,32}.txt`; secondary `r6-pipeline-sample-t{1,8,32}.txt`.

### Finding #2 from PERF_ANALYSIS-2026-08-29T11-01-08 — **Confirmed (small; low-priority tidy-up)**

- Claim under test: five `RecordHeader` wrappers are allocated per event for five constant headers in `ResilientMessageSender.buildRecord`; a shared pre-built header list would remove them.
- Instrument: JMH `-prof gc`, average time — `gc.alloc.rate.norm` as primary result (deterministic; here the record escapes by being returned, so escape analysis cannot mask the mechanism).
- Baseline vs. candidate: production shape (record + 5 × `headers().add`) vs. `ProducerRecord(…, Iterable<Header>)` with one shared immutable list; header names/value sizes mirror the enricher's real static set; 1 KB payload, real-length key.
- Decision rule (fixed before the run): mechanism confirmed at a saving ≥ ~150 B/op; retired **for action** if the saving is < 5 % of the delivered path's per-event allocation.
- Result: baseline **304.000 ± 0.001 B/op**, 37.5 ± 0.2 ns/op; candidate **144.000 ± 0.001 B/op**, 14.7 ± 0.5 ns/op → saving **160.0 B/op** and ~22.8 ns/op (32 B × 5 wrappers — the counted mechanism appearing verbatim in the measurement). Fork variance: none (identical to the third decimal).
- System translation: measured pipeline allocation is ≈ 778 B/op caller-side (clean R5) + ≈ 272 B/op sender-side unbound (clean R2) ≈ **1.05 KB/event as a lower bound** — the escape-analysis caveat applies: R2's sender path measured *less* than R1's isolated record construction (272 < 304 B/op), demonstrating that the inlined discarding producer lets the JIT eliminate part of the record graph; with a real, escaping producer the production total is higher and the saving's share correspondingly lower. The 160 B/op saving is therefore **between ~5 % and ~15 %** of the per-event allocation depending on how much of the record graph escapes in production — at the assumed 10 k events/s, ~1.6 MB/s of young-gen churn either way.
- Verdict: **confirmed** — `Effect: measured` (160.0 B/op, ~23 ns/op). Priority **P3**: real, exactly quantified, and small; fold into the next touch of the enricher/sender rather than dedicating a session (it also strengthens the documented shared-immutable-header convention).
- Change cost: low — extends the shared-read-only convention by one object level; the contract must cover the shared `Header` objects.
- Raw output: `./benchmarks/results/2026-08-29/r1-recordheaders.txt`.

### Finding #3 from PERF_ANALYSIS-2026-08-29T11-01-08 — **Confirmed as modest; retired for action at realistic rates**

- Claim under test: binding metrics attaches a per-delivered-event envelope (capturing callback lambda, `Duration` box, Resilience4j event objects via the attached breaker consumers, meter updates); statically classified `< 10 objects`, "small".
- Instrument: JMH `-prof gc` + average time on `SenderPathBenchmark` — the isolated delivered path (`ResilientMessageSender.send` with instant-success callbacks), single-threaded, `metricsBound=false/true` the only variable, production wiring for the bound case (`MetricsBindings.bind`, breaker event consumers attached exactly as `bindMeterRegistry` does). Full-pipeline measurement was rejected for this finding because open load saturates the worker and the envelope never runs on the overflow path.
- Baseline vs. candidate: same code, unbound (NO_OP hook) vs. bound (`SimpleMeterRegistry`).
- Decision rule (fixed before the run): the bound-vs-unbound delta of `gc.alloc.rate.norm` is the envelope; retire for action if its absolute cost at the assumed profile is negligible; escalate only if it is a substantial share at realistic rates.
- Result (clean run): unbound **272.001 ± 0.001 B/op**, 94.0 ± 2.9 ns/op; bound **482.7 ± 58.4 B/op**, 213.8 ± 6.2 ns/op → envelope = **+210.7 B/op and +119.8 ns/op per delivered event**. Confidence intervals of baseline and bound do not overlap on either axis. (The contaminated first pass had reported ~18× this allocation delta; see the discard note.)
- Fork variance: the bound variant's allocation norm varies ±58 B/op across forks (unbound is exact) — consistent with JIT-profile-dependent elimination of parts of the envelope (lambda/`Duration` may or may not escape once the discarding producer inlines); the measured delta is therefore a **lower bound with fork-dependent spread**, and a production registry (e.g. Prometheus, with histogram recording) will sit at or above it.
- System translation: at the assumed 10 k delivered events/s ≈ **2.1 MB/s** additional allocation and ≈ 0.12 % of one core; at 100 k/s ≈ 21 MB/s and ≈ 1.2 % of one core. Relative to the measured (lower-bound) pipeline allocation of ~1.05 KB/event the envelope is ~17 %; relative to a production total with an escaping record graph, less.
- Verdict: **confirmed as modest** — `Effect: measured` (+210.7 B, +119.8 ns per delivered event under `SimpleMeterRegistry`); the input's static "small" estimate was correct. **Retired for action at the stated profile** (and comfortably defensible up to ~100 k events/s); the optimization sketches from the input report stay on file for hosts beyond that, with this benchmark (re-run against the production registry implementation) as the gate. Priority after measurement: **P3 → no action**.
- Change cost: n/a at this verdict (candidates would be internal-seam API changes; not recommended on these numbers).
- Raw output: `./benchmarks/results/2026-08-29/r2-senderpath.txt` (supporting: `r5-pipeline-gc.txt` — caller-side bound/unbound delta ~15 B/op, i.e. the envelope is almost entirely worker/callback-side).

## 7. Side observations (unmeasured as findings; candidates for a future analysis)

- **Escape analysis visibly eliminates non-escaping record graphs:** the isolated record construction (returned → escapes) allocates 304 B/op while the full sender path over an inlined discarding producer allocates only 272 B/op total — direct evidence that pipeline-level alloc totals from mock-backed benchmarks are lower bounds. Any future absolute-allocation claim should come from a host profile with a real producer (input plan M1).
- **The shedding design works under saturation** (path-mix counters, clean run): open-loop callers pushed roughly 7 M accepted events/s through `doAppend` with ~76 % diverted (trial-cumulative counters: ~70 M accepted, ~52 M diverted), while caller p99 stayed at 0.4 µs single-threaded; the overflow path is itself very cheap. Worth an operator-docs sentence at most.
- **Caller-side metrics delta is trivial** (~15 B/op on the divert-dominant path) — the envelope is worker/callback-side, confirming where any future optimization would have to act.
- **Default-context logging is a real deployment hazard for benchmarks and tools embedding the library's dependencies:** an unconfigured Logback context at DEBUG turns Resilience4j into a per-call logger. For the library itself this is the host's configuration responsibility; for this repo's benchmark module it is now pinned OFF.
- **JDK skew:** measurements ran on JDK 26 against a Java-21-target library; a CI-grade rerun on Temurin 21 would remove the caveat. Nothing observed suggests a direction change.
