## 1. Executive summary of the follow-up pass

The initial pass concentrated on the four score-5 files and found its defects at the edges of the lifecycle; this round shifted to the residual risk: the score-1/2 files that were only skimmed (`MessageEnricher`, `TopicMappingConfig`, `TopicRouter`, the properties parser), the interaction of the fresh remediation code with the rest of the pipeline (restart path, metrics binding, callback accounting), the operator-facing documentation as a behavioral contract, and the build descriptor. The result is modest and the overall picture has not shifted: **one new Medium and four new Low findings, one new systemic pattern, no Critical or High, no severity change to a previous finding.** The Medium is a second-order defect the initial pass and the 2026-08-29 remediation both missed: in a `LoggerContext` without a bound MDC adapter (the "embedded" setup the previous fix explicitly catered for), the swallowed `prepareForDeferredProcessing` failure is immediately followed by the same `NullPointerException` from the default partitioning-key extractor, so *every* event diverts to the fallback with reason `encoder.error` - the appender never ships to Kafka in that setup, reported once. Three of the four Lows are consequences of the initial round's own fixes: the configuration guide still documents the 200 ms drain window that finding 3 removed, the Spring binding cannot rebind a restarted appender instance although the restart support of finding 4 now makes that path real, and a restart carries an OPEN breaker over into the new pipeline. The fourth Low is documentation promising a per-class circuit-breaker override that no public API can reach since ADR-0002. The build checks came out clean: the lz4 security pin resolves to a single artifact, the version resource is filtered, the benchmark module uses the mangled `internal` names by design. **Test verdict (tests remained in scope):** unchanged in substance from the initial pass after the remediation - the suite is deterministic where the structure allows it and now closes what it opens; the one anomaly this round adds is a convention gap, not an evidential one: 128 of 269 test methods lack the three-question rationale block that CONTRIBUTING requires, and the generated test-evidence page shows them as undocumented (pattern P4). The MDC-less path of finding R2-1 has no test because every test fixture sets the MDC map explicitly - the fixture hides exactly the production condition.

### 🟡 Medium

- [x] R2-1. [`./src/main/kotlin/eu/inqudium/tabellarium/MessageEnricher.kt:210`] {Medium} {Confidence: high} {robustness / correctness} {Status: NEW} In a `LoggerContext` without a bound MDC adapter the default partitioning-key extractor throws the very `NullPointerException` that `append()` swallows one step earlier, so every event fails the hot path
  - Symptom → cause: `KafkaAppender.append` (`./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:657-663`) catches the `RuntimeException` from `event.prepareForDeferredProcessing()` with the comment "deliver the event as-is rather than failing the hot path" - the case addressed by the 2026-08-29 remediation for an embedded context. In logback-classic 1.5.38, `LoggingEvent.getMDCPropertyMap()` dereferences `loggerContext.getMDCAdapter()` (`LoggingEvent.java:456-461`); a `LoggerContext` that was constructed directly rather than through `LogbackServiceProvider` has a null adapter (`LogbackServiceProvider.java:57` is the only place that sets it), so the NPE is deterministic for that context. Twelve lines later `messageEnricher.enrich(event)` (`KafkaAppender.kt:675`) runs `DEFAULT_TRACE_ID_EXTRACTOR`, which reads `event.mdcPropertyMap` (`MessageEnricher.kt:210`) - the same getter, the same NPE - now outside the guarded block: the hot-path catch reports it once as "Hot path error", counts `encoder.error`, and diverts the event to the fallback. Every subsequent event takes the same path silently.
  - Trigger condition: only edge case - a `LoggerContext` without an MDC adapter (programmatically embedded Logback, some test harnesses); the standard SLF4J-bootstrapped context is unaffected. Deterministic once the condition holds.
  - Impact: wrong result / silent total loss of Kafka delivery in that setup - the appender starts successfully, reports one error, and ships nothing; with no fallback configured every event is dropped. The code comment documents behavior that does not exist.
  - Relation: standalone in this chain; it is the unfinished half of the 2026-08-29 fix for finding 1 of `./docs/assessment/CODE_ANALYSIS-2026-08-29T00-03-57.md` (materialize lazily on the caller thread), whose "degrade gracefully" claim only covered `prepareForDeferredProcessing`.
  - Test risk gap: every test event is built by `newTestLoggingEvent` (`./src/test/kotlin/eu/inqudium/tabellarium/TestEvents.kt:28`), which sets the MDC map explicitly *because* the bare context would NPE - the fixture hides the production condition, so no test exercises an event whose MDC is unreadable end-to-end (the `MessageEnricherTest` null-map case stubs the getter to return null, not to throw).
  - Fix strategy: make the default extractor tolerate an unreadable MDC (treat a failing `getMDCPropertyMap` as "no key"), or have `append` fall back to an empty MDC snapshot when materialization fails so that neither the enricher nor a fallback layout can hit the adapter again; add an appender-level test with a bare `LoggerContext` event and a non-stubbed MDC.
  - **Status:** Fixed in `5d849c8` (2026-09-07). Two guards: `append()` pins an empty MDC snapshot on the event (`LoggingEvent.setMDCPropertyMap`) when materialization fails, so encoder, extractor and fallback layout never hit the adapter again; independently, `DEFAULT_TRACE_ID_EXTRACTOR` treats an unreadable MDC as "no key". New appender-level test with an event on a bare `LoggerContext` (no map set) asserting delivery without a key and no hot-path error; new enricher test with a throwing getter. Mutation check: removing both guards fails the appender test.

- [x] R2-5. [`./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:475`] {Low} {Confidence: high} {robustness / lifecycle} {Status: NEW} A restart reuses the appender's `CircuitBreakerRegistry`, so breaker state (OPEN, HALF_OPEN counters, sliding window) survives into the rebuilt pipeline

  - Trigger condition: only on a programmatic restart while a breaker is not CLOSED.
  - Impact: bounded wrong result (up to 30 s of avoidable fallback diversion per class), visible in metrics; no loss beyond the fallback semantics.
  - Relation: consequence of #4 (linked).
