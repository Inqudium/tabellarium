## 1. Executive summary

No measurement artefacts were supplied; this is a **hypothesis-generating static analysis**, and nothing below is a measured figure. Under the assumed load profile the appender's runtime cost is dominated by work it *delegates by design*: the encoder call and Logback's deferred-processing materialization on the caller thread, and `producer.send` plus compression on the per-class worker — the appender's **own** added cost per event is a thin envelope (guards, routing map lookups, one bounded-queue hand-off, and, when metrics are bound, the instrumentation hooks) estimated in the low single-digit microseconds of CPU and a few hundred bytes of transient allocation per event. The architecture is performance-honest: hot-path work is O(1) with no locks on the caller side beyond the queue hand-off, every buffer is bounded, all expensive constructions (regex, headers, meter resolution, client ids) happen once at startup, and there is **no unbounded retention anywhere** — the lifetime story is clean (transient envelope, batch-scoped queues, small global singletons). What the analysis finds is correspondingly modest: one real per-event allocation cluster that could be pre-built (Kafka record headers, finding 1), one concurrency mechanism whose behaviour at high fan-in deserves a measurement before anyone worries (the `LinkedBlockingQueue` put-lock, finding 2), the per-event metrics envelope as the price of observability (finding 3), and three P4 items explicitly recommended to leave alone — one of which is mainly a documentation bug (an `EnumMap` claim the code does not implement, finding 4).

**Performance verdict:**

1. **Dominant cost:** CPU per event, and it sits in the delegated stages (encoder ≫ appender envelope; producer/compression on the worker). The appender's own contribution is allocation-light and lock-free on the caller path; judgment rests on complete code reading, not measurement.
2. **Scaling risk:** nothing breaks by mechanism — growth degrades *visibly by design*: at sustained rates above what one worker per class can push through `producer.send` (`max.block.ms`-capped), the bounded send queue overflows to the fallback with counted `queue.full` diversions rather than latency or heap growth. The first *silent* cost to grow is put-lock contention on the send queue at high caller fan-in (finding 2), plausibly relevant only well above the assumed operating point (≥ ~10× at high thread counts). Peak heap is capped by construction: `(sendQueueCapacity × classes + fallback capacity) × event-graph size` — with defaults and 1 KB events roughly a few MB per class path (estimate).
3. **Highest leverage:** honestly, none needed at the assumed load — the system is already shaped so its costs are the unavoidable ones. If a host profile ever shows the appender itself: pre-built shared record headers (finding 1) is the one cheap, proven-mechanism win; everything else is measure-first.

## 2. Scope & methodology

Stack: pure-Kotlin Logback appender library; no Spring MVC/WebFlux, no coroutines, no persistence of its own — the *host's* threading model matters only at the caller boundary (the appender never blocks callers and takes no locks on them; virtual-thread interaction is limited to two `ThreadLocal` guards, see finding 6). Concurrency model: one daemon worker per active topic class (send), one fallback worker, Kafka's own network thread(s); hand-off via bounded `LinkedBlockingQueue`s. Serialization boundary: the injected Logback encoder (payload bytes produced once per event on the caller). Observability: **present and opt-in** — Micrometer counters/timers/gauges with pre-resolved meters, plus per-producer Kafka client metrics and breaker meters; the absence-of-instrumentation finding this prompt anticipates does not apply. Evidence base and load profile: see the metadata block; all frequencies below are assumptions from it. Method: complete read of all 17 production files (all fully known from this session and re-verified at this commit), lifetime classification per allocation site, boundary attribution for encoder/Kafka costs. Blind spots: encoder and Kafka client internals (boundaries); real consumer load profiles; any JIT-dependent magnitude (flagged as measure).

### 🟡 P3

- [ ] 1. [`./src/main/kotlin/eu/inqudium/tabellarium/ResilientMessageSender.kt:272`] {P3} {Evidence: proven} {Cost type: allocation} {Lifetime: transient} Five `RecordHeader` wrappers are allocated per event for five constant headers
  - Mechanism: `buildRecord` loops the five pre-encoded static headers into `record.headers().add(name, valueBytes)`; each `add` wraps name+bytes in a new Kafka `RecordHeader`. The *values* are pre-encoded once (good — that was the expensive part), but the immutable wrapper objects are re-created per event although they never vary.
  - Per execution: ~5 objects, ~200 bytes (estimate); pure young-gen churn, no retention (the record graph dies after the send callback).
  - Frequency: per event — 1–10 k/s assumed.
  - Aggregate: ~0.2–2 MB/s allocation (estimate) — trivial against a typical service baseline, which is why this is P3 and not P2.
  - Scaling: linear in event rate; at 100 k/s it is ~20 MB/s of avoidable churn, still young-gen-only.
  - Verification: async-profiler in alloc mode on a host app at fixed event rate; look for `RecordHeader`/`RecordHeaders` allocation share attributed to `buildRecord`.
  - Optimization sketch: pre-build one immutable shared `Header` list in `MessageEnricher` (the wrappers are immutable and Kafka reads them read-only) and pass it to the `ProducerRecord` constructor that accepts `Iterable<Header>`; only the per-event key/value remain per-record.
  - Change risk: low — extends the existing shared-read-only-array convention (canonically documented on `EnrichedRecord.headers`) by one object level; the read-only contract must cover the shared `Header` objects too.

- [ ] 2. [`./src/main/kotlin/eu/inqudium/tabellarium/SendDispatcher.kt:137` (queue), `:226` (offer)] {P3} {Evidence: probable} {Cost type: CPU/contention} {Lifetime: transient (queue nodes)} The multi-producer hand-off is a `LinkedBlockingQueue` put-lock — fine at the assumed load, the first silent scaling cost above it
  - Mechanism: every logging thread's `dispatch` takes the queue's `putLock` (plus one node allocation per event); all callers of one topic class contend on a single `ReentrantLock`. Uncontended this is tens of nanoseconds; under high fan-in (many threads, high rate) it becomes the only synchronization point on the caller path and serializes it.
  - Per execution: ~20–50 ns uncontended + 1 node (~40 B) (estimates); contention cost is unknowable statically.
  - Frequency: per event; contention scales with caller-thread count × rate per class.
  - Aggregate: negligible at the assumed 1–10 k/s with ≤ 64 threads; potentially measurable at ≥ ~100 k/s bursts with high thread counts.
  - Scaling: this is the point of the finding — cost is a function of concurrency × rate, both operator-controlled; at 10× the assumed load the lock is plausibly still fine, at 100× it is the first thing to profile.
  - Verification: JFR `JavaMonitorEnter`/thread-park events or async-profiler lock mode on a saturating multi-thread producer benchmark against one appender; refutation = put-lock wait time remains a negligible share at the target load.
  - Optimization sketch: only if measured — an MPSC queue (e.g. JCTools) behind the same bounded/overflow semantics; costs a new dependency and re-verification of the close/drain accounting, which is why measurement comes first.
  - Change risk: medium — the drain/overflow/close accounting is the most carefully tested part of the module; do not touch without the measurement.

- [ ] 3. [`./src/main/kotlin/eu/inqudium/tabellarium/ResilientMessageSender.kt:221` (callback lambda), `:223`/`:245` (`Duration.ofNanos`), `./src/main/kotlin/eu/inqudium/tabellarium/MetricsBindings.kt:326` (breaker event consumers)] {P3} {Evidence: probable} {Cost type: allocation + CPU} {Lifetime: transient} The per-event observability envelope: capturing callback lambda, `Duration` box, and Resilience4j event objects once metrics are bound
  - Mechanism: each send allocates one capturing callback lambda (unavoidable for the outcome contract) and one `Duration` per completion; additionally, because `MetricsBindings` attaches breaker event consumers, Resilience4j allocates a success/error event object (with its own timestamp) per call — R4j only does this when consumers exist, i.e. exactly in the documented recommended setup. Plus 3–4 Micrometer counter/timer updates per event.
  - Per execution: ~3–5 small objects, ~150–300 B, plus ~100–300 ns meter updates (estimates).
  - Frequency: per event when `bindMeterRegistry` was called; assumed the normal case.
  - Aggregate: at 10 k/s ~2–3 MB/s and ≪ 1 % CPU (estimates) — the reasonable price of the metrics the operator asked for.
  - Scaling: linear in event rate; relevant to inspect only at ≥ 50–100 k/s per instance.
  - Verification: async-profiler alloc mode with and without `bindMeterRegistry`; look at the delta share of `CircuitBreakerOnSuccessEvent`, lambda, and `Duration` allocations.
  - Optimization sketch: if a host profile ever flags it — record elapsed nanos through a long-based hook instead of `Duration`, and consider making the breaker *call* meters poll-based rather than event-consumer-based; both are API-shape changes inside the internal metrics seam.
  - Change risk: medium — touches the metrics contract; the current shape mirrors the official binder semantics deliberately.

## 7. Measurement plan

Ordered by information gain per effort; every step names the refutation condition:

1. **Host-app allocation profile (confirms/refutes findings 1, 3, 6 and the pattern):** async-profiler in alloc mode on any consuming service (or a minimal Spring Boot host) logging at a fixed 10 k events/s with metrics bound, 30 s window. Signal: allocation share attributed to `eu.inqudium.tabellarium.*`, `RecordHeader`, `CircuitBreakerOn*Event`, `Duration`. Refutation: appender-attributed allocation < ~1–2 % of the host's baseline rate → close findings 1 and 3 as not worth the change risk.
2. **Caller-path latency + hand-off contention (finding 2):** JMH benchmark (to be written in a fix session, not here): N caller threads invoking `doAppend` against a started appender with a no-op-fast `ProducerFactory`; parameters: threads ∈ {1, 8, 32, 128}, rate open-loop; plus JFR `JavaMonitorEnter` on the same run. Signal: p99 `doAppend` latency and put-lock wait share vs. thread count. Refutation: flat p99 and negligible lock wait at 32+ threads → finding 2 stays a non-issue at any realistic load. Pitfalls to respect: consume the encoder output (dead-code elimination), warm up past C2, do not measure `MockProducer` internals as if they were Kafka.
3. **Steady-state CPU attribution (verdict check):** async-profiler CPU mode on the same host run. Signal: encoder vs. appender-envelope vs. kafka-clients share on the caller and worker threads. Refutation of the verdict: appender envelope > encoder share would invalidate this report's dominant-cost claim and re-open H1 for a deeper pass.
4. **Degraded-mode behaviour (H4, no finding today):** same host with the broker stopped; watch `kafka.appender.events.fallback` rates, fallback queue gauges, and GC behaviour during the burst. Signal sought: bounded heap (queue caps holding) and no promotion spike; a promotion spike would justify revisiting queue capacity defaults.

## 8. Examined and unremarkable

Checked and found unproblematic (with the deciding observation each): **regex/expensive object construction** — all `Regex`/patterns, client ids, static headers, meter instances are built once at startup or bind time, nothing per event; **strings on the hot path** — no concatenation, formatting, or case conversion per event outside the encoder boundary (violation/diagnostic strings are startup- or error-path-only); **exceptions as control flow** — none; the hot path's try/catch costs nothing when not throwing, and log-storm suppression caps the error path; **boxing** — none found per event (`ThreadLocal<Boolean>` uses cached constants; no nullable primitives on hot paths); **`Enum.values()`** — the codebase uses cached `entries` throughout; **collection pipelines on hot paths** — none (the `associateWith` chains of finding 4 run once at bind time; per-event code is straight-line); **unbounded retention** — none anywhere: both queue types are capacity-bounded, drop/divert counters are primitives, `MetricsBindings` holders are bounded by breaker count, meters are deregistered on stop (leak-free rebind cycles are explicitly tested); **caches** — none beyond the intentional startup-computed constants (headers, client ids), so no eviction/stampede surface; **reflection** — none at runtime (one `Class.forName` probe at bind time); **backpressure** — bounded queues with counted overflow by design; peak retention is `capacity × event-graph size × (classes + 1)`, operator-tunable via `<sendQueueCapacity>`; **reactive/coroutines/persistence** — not present; **startup** — eager producer construction and meter pre-resolution are once-per-configuration and documented (the 32 MB-per-producer buffer footprint at multiple active classes is a *documented* consolidation trade-off in the README's future work, not re-litigated here); **worker idle cost** — 100 ms poll timeouts wake each worker 10×/s idle, negligible; **time sources** — two reads per send, justified (finding 5).


> **Addendum (2026-08-29, post-analysis; the sanctioned status/addendum edit per the repo's report convention):** review discussion asked whether the **producer self-logging guard** (`./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:594` — `threadName.startsWith(PRODUCER_NETWORK_THREAD_PREFIX) && threadName.removePrefix(…) in producerClientIds`) was examined or overlooked. It was examined during Phase 2 but wrongly omitted from this section — recorded now for the audit trail. Assessment: the **fast path** (every ordinary event) is a lazily-captured, event-cached thread name plus a `startsWith` that fails on the first character for non-Kafka thread names — ~2–5 ns, zero allocation (estimate); a precomputed full-name set lookup would be *slower* here, so there is nothing to gain where it counts. The **slow path** (prefix matches — i.e. every log event from *any* Kafka producer network thread in the JVM, including the application's own producers, whose events then proceed via set miss) allocates one transient substring (~60–80 B) plus its hash for the set lookup; frequency is the JVM's Kafka-client logging rate, ~0/s in steady state and at most tens/s during broker incidents. A zero-allocation variant exists (precompute `prefix + clientId` full names at `buildPipeline`, keep the `startsWith` prefilter, then membership-test the original string), saving ~60 B + ~20 ns per such event. **Verdict: P4, leave unchanged** — cost × frequency is below any measurement threshold even in the degraded case, and the change would add a second derived structure (including the blank-client-id exclusion rule) for no measurable gain.
