## 1. Executive Summary

The attack surface is **structurally small, and the code makes almost no security-relevant mistakes**. This is a library, not a service: there is no network listener, no request handling, no HTTP entry point, no persistence, no template rendering, no session or auth logic, and no Actuator — so the classic OWASP web categories (SQLi, XSS, CSRF, IDOR, open redirect, mass assignment) are *structurally* inapplicable rather than merely unobserved. The dangerous-API catalogue comes back essentially empty: no `Runtime`/`ProcessBuilder`, no `ObjectInputStream`/`XMLDecoder`, no SpEL/script/Groovy evaluation, no JNDI lookup, no XML parsing, no cryptography, no `java.util.Random`, no trust-all `TrustManager`. The only `Class.forName` calls take hardcoded string literals as optional-dependency probes. Serialization is one-directional (`ByteArraySerializer`, forcibly set) — the appender never deserializes untrusted bytes, which removes the JVM's most damaging vulnerability class by construction. **No Critical and no High findings were identified.**

What remains is the profile of a **data-egress component**, and that is where the three Medium findings sit. First, the one attacker-influenceable input that genuinely flows through this code — log-event data — reaches Kafka record attributes with **no size bound**: an MDC `traceId` that a host application bridged from an inbound header becomes the record key verbatim, which enables partition pinning and oversized records that (by the breaker's deliberate ignore-list) flood the fallback appender indefinitely instead of tripping the circuit. Second, the appender enforces compliance-grade *durability* for AUDIT topics through mandatory overrides but stays entirely silent about transport *confidentiality* — audit logs shipped over `PLAINTEXT` produce no startup signal, which is inconsistent with the project's own stated philosophy. Third, `jackson-databind` sits at `compile` scope in the consumer-visible POM although the shipped code does not use Jackson at all, pushing a historically gadget-chain-prone library onto every consumer's runtime classpath. Credential handling itself is sound: the recently added debug output is credential-safe by construction (a diff against the operator's base properties can only ever contain the fixed, non-sensitive override keys), and the only secret-looking string in the repository is a synthetic JAAS test fixture.

## 2. Scope & Methodology

- **Audited:** all 16 production files under `./src/main/kotlin/eu/inqudium/tabellarium/`, read completely and traced along the taint model below; `./pom.xml` incl. the resolved runtime tree and the flattened (consumer-visible) descriptor; both CI workflows and the Dependabot configuration.
- **Not audited as attack surface:** test sources (they do not ship) — they were, however, grepped for committed credentials; documentation (grepped likewise, and reviewed for credential-handling guidance since `./SECURITY.md` names credential leakage as an in-scope concern).
- **Detected stack:** Kotlin 2.4.10 / JDK 21 library. Spring is **optional** (`spring-context`, used only by the opt-in `@Configuration` binding class); there is **no Spring MVC, no WebFlux, no Spring Security, no persistence layer**. Messaging is Kafka **producer-only** (`kafka-clients` 4.2.1, resolved via the Boot BOM). Resolved runtime tree also includes logback 1.5.38, slf4j 2.0.18, resilience4j 2.4.0, micrometer 1.17.1 (optional), logstash-logback-encoder 9.0 (optional), jackson-databind 2.21.5 (see finding 3), snappy-java 1.1.10.7 and zstd-jni (Kafka compression codecs).
- **Taint model applied:** the only untrusted *source* reaching this code is the **log event itself** (message, MDC, markers, throwable) — attacker-influenceable whenever the host application logs user-controlled data. The *sinks* it can reach are the Kafka record's value (encoder output), key (partitioning key), and headers (static config), plus Logback's status manager (information disclosure) and the fallback appender. Producer configuration (`<kafkaProducerProperties>`, incl. credentials) is an **operator-controlled**, trusted source — but a *sensitive* one, so every path from it to log/status output was traced.
- **Verification:** read-only, static. No local Kafka broker, no exploit execution, no live requests (per the scope boundary; no go-ahead requested). Findings 1 and 2 are reachability-conditional on the *consuming application's* configuration, which lives outside this repository — stated per finding.
- **Known limitations / blind spots:**
  - **No automated dependency-CVE scan was run.** OWASP Dependency-Check/Snyk are not configured in this build, and running them here would require pulling the full NVD feed. Compensating control in place: **Dependabot** (`./.github/dependabot.yml`, weekly, Maven + GitHub Actions, minor/patch grouped) — which alerts on *published advisories only*.
  - **Knowledge-cutoff limitation (important):** several resolved versions post-date this auditor's January 2026 knowledge cutoff (Spring Boot 4.1.1 → spring-core 7.0.9, kafka-clients 4.2.1, jackson-databind 2.21.5, logback 1.5.38, micrometer 1.17.1). I can state that the *classic* JVM catastrophes do not apply **structurally** — there is no `log4j-core` on the tree at all (Log4Shell N/A), no SnakeYAML parsing in this code, no Java native deserialization, and no Spring MVC/WebFlux data binding (Spring4Shell N/A) — but I **cannot assert freedom from CVEs for those specific version numbers**. A dependency-scanner run remains necessary for that statement.
  - Consumer-side configuration (TLS settings, MDC bridging, fallback-file placement and rotation) is not visible from this repository and materially determines the exploitability of findings 1, 2 and 5.

### 🟡 Medium

- [x] 1. [`./src/main/kotlin/eu/inqudium/tabellarium/MessageEnricher.kt:166` → `./src/main/kotlin/eu/inqudium/tabellarium/ResilientMessageSender.kt:247`] {Medium} {Confidence: medium} {CWE-770 (Allocation Without Limits), OWASP A04:2021 Insecure Design} Unbounded partitioning key derived from MDC — enables partition pinning and a self-sustaining fallback flood
  - Source → Sink: the default extractor reads MDC `traceId` (`MessageEnricher.kt:166`) with a blank check but **no length or character bound**, and `buildRecord` converts it verbatim into the Kafka record key (`ResilientMessageSender.kt:247`). The MDC is attacker-influenceable whenever the host application bridges a request header into it — a common pattern with custom `X-Request-Id`/`X-Trace-Id` propagation (standard Micrometer/Brave tracing generates the id internally and is *not* affected).
  - Impact: (a) **partition pinning** — an attacker who controls the id can steer all of their records onto a single partition, skewing the destination topic and the consumers behind it; (b) **record inflation** — a multi-hundred-kilobyte header value becomes the record key, and once the record exceeds `max.request.size` the send fails with `RecordTooLargeException`, which is deliberately on the circuit breaker's ignore list (`ResilientMessageSender.kt:326`). The breaker therefore never opens, and every such event is routed to the fallback appender **indefinitely** — turning a client-side input into sustained write amplification on the fallback file (disk exhaustion) or, without a fallback, silent loss of those events. The ignore-list decision is correct on its own terms; the missing bound is what makes it exploitable.
  - Reachability: not from outside this library alone — requires the consuming application to place attacker-influenceable data into MDC `traceId` (or to configure an equivalent custom extractor). No authentication bypass, no code execution; the impact is availability and data-quality of the logging pipeline.
  - Fix strategy: bound the partitioning key at the enricher (truncate or reject beyond a small limit — trace ids are ≤ 32 hex characters in every established format), and document the bound as part of the custom-extractor contract.

- [x] 2. [`./src/main/kotlin/eu/inqudium/tabellarium/ProducerPropertiesBuilder.kt` / `./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:222` — the absence of any handling] {Medium} {Confidence: high} {CWE-319 (Cleartext Transmission of Sensitive Information), OWASP A02:2021 Cryptographic Failures} Audit-grade log streams can be shipped over `PLAINTEXT` without any startup signal
  - Source → Sink: `security.protocol` and the whole SSL/SASL block are passed through from `<kafkaProducerProperties>` to the Kafka client untouched (verified: no occurrence anywhere in `./src/main/kotlin/` outside KDoc examples). The appender enforces mandatory `acks=all` and `enable.idempotence=true` for the AUDIT class and warns loudly when an operator value is overruled — but it applies no comparable check, and emits no warning, when a topic classified `AUDIT` is served by a producer configured for cleartext transport.
  - Impact: BaFin/MaRisk-relevant audit records — which by this project's own framing must not be silently weakened — traverse the network unencrypted and unauthenticated; anyone on the path can read or tamper with the audit trail. The gap is one of *signalling*: the operator receives an explicit warning when durability is weakened, and complete silence when confidentiality is absent.
  - Reachability: configuration-dependent (operator sets or omits `security.protocol`); no attacker action is needed to *create* the condition, only network position to exploit it. Not reachable at all in deployments that configure SSL/SASL_SSL, which the shipped example does.
  - Fix strategy: at startup, when an AUDIT (or FUNCTIONAL) class is active and the effective `security.protocol` is absent or `PLAINTEXT`, emit a status **warning** in the same style as the mandatory-override notice — enforcement would over-reach into operator territory, but silence is inconsistent with the appender's stated compliance posture.

- [x] 3. [`./pom.xml:191`] {Medium} {Confidence: high} {CWE-1395 (Dependency on Vulnerable Third-Party Component — closest fit; no known CVE is asserted for 2.21.5), OWASP A06:2021 Vulnerable and Outdated Components} `jackson-databind` is a consumer-visible `compile` dependency although the shipped code does not use Jackson
  - Source → Sink: the dependency is declared at `compile` scope with an inline comment stating it is used *"only by the tests"*; the flattened, consumer-visible POM (`target/.flattened-pom.xml`) therefore carries it as a non-optional dependency, and it resolves to `jackson-databind:2.21.5`. A grep over `./src/main/kotlin/` confirms **zero** Jackson references in shipped code — the encoder does its own JSON work inside `logstash-logback-encoder` (itself correctly marked `optional`).
  - Impact: every application that adds this appender inherits `jackson-databind` on its runtime classpath. Two consequences: it enlarges the consumer's attack surface with the JVM library that has historically carried the most deserialization gadget-chain CVEs, and it can silently pin or upgrade the Jackson version in applications that manage Jackson themselves — a dependency-conflict and downgrade-risk vector rather than a directly exploitable flaw here.
  - Reachability: not exploitable through this library (no Jackson code path exists in it); the exposure materialises in consuming applications and only in combination with their own usage.
  - Fix strategy: move the dependency to `test` scope (matching its documented purpose); consumers that need Jackson already declare it themselves.

### 🟢 Low

- [x] 4. [`./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:227`] {Low} {Confidence: medium} {CWE-209 (Information Exposure Through an Error Message)} Producer-construction failures forward the raw exception message **and the full stack trace** to Logback's status manager (`addError("Failed to build KafkaAppender pipeline: ${e.message}", e)`), which typically prints to console/stdout and is scraped by log collectors. The exception originates in the Kafka client, constructed from credential-bearing configuration; Kafka masks `Password`-typed values in its own output, so a direct credential echo is unlikely — but the content of that text is outside this appender's control, while `./SECURITY.md` explicitly claims credential leakage through status messages as an in-scope concern. Reachability: startup-time only, requires a misconfiguration to trigger. Fix strategy: log the exception type and a bounded, appender-authored message, and keep the stack trace behind the `<debug>` flag.
- [x] 5. [`./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:359`] {Low} {Confidence: high} {CWE-117 (Improper Output Neutralization for Logs)} The appender is encoder-agnostic and ships the encoder's bytes verbatim as the record value. With the recommended `LogstashEncoder` the event is JSON-escaped and structurally safe; with a `PatternLayoutEncoder`, a CRLF sequence in attacker-influenced message text produces forged extra records in the destination topic, poisoning downstream log analysis and alerting. The documentation recommends the JSON encoder for parseability but never states the security implication of that choice. Reachability: requires a non-JSON encoder configuration *and* unsanitised user input in log messages. Fix strategy: state the security rationale (not just the parseability rationale) for the JSON encoder recommendation in the configuration guide.
- [x] 6. [`./.github/workflows/ci.yml:1`] {Low} {Confidence: high} {CWE-732 (Incorrect Permission Assignment) — least privilege} The CI workflow declares no `permissions:` block, so it inherits the repository default for `GITHUB_TOKEN`. The **effective state is currently correct** (verified via API: `default_workflow_permissions=read`), and the sibling `docs.yml` does declare its permissions explicitly — so this is defence in depth: a repository-level settings change by any admin would silently widen the token for a workflow that also runs on fork pull requests. Fix strategy: add an explicit `permissions: contents: read` block, matching `docs.yml`.
- [x] 7. [`./.github/workflows/ci.yml:16`, `:17`; `./.github/workflows/docs.yml`] {Low} {Confidence: high} {CWE-1357 (Reliance on Insufficiently Trustworthy Component)} Third-party actions are pinned to mutable major tags (`actions/checkout@v7`, `actions/setup-java@v6`, `actions/setup-python@v5`, `actions/upload-pages-artifact@v3`, `actions/deploy-pages@v4`) rather than commit SHAs. A compromised or retagged release would execute in CI — for `docs.yml` with `pages: write` and `id-token: write`. All actions are first-party GitHub-published, which lowers but does not eliminate the risk. Fix strategy: pin to full commit SHAs with a version comment and let Dependabot (already configured for `github-actions`) propose the bumps.

## 6. Systemic Patterns

1. **Attacker-influenceable log-event data reaches Kafka record attributes without any size or content bound.** The appender derives all three record attributes from event data or configuration, and applies a bound to none of them: the **key** (from MDC, finding 1 — unbounded length), the **value** (encoder output, finding 5 — no structural guarantee beyond the operator's encoder choice), and the **headers** (config-derived, therefore trusted — the one attribute where the input is not attacker-influenceable). **3 record attributes, 2 of them affected** (counting basis: complete read of `MessageEnricher.enrich`/`DEFAULT_TRACE_ID_EXTRACTOR` and `ResilientMessageSender.buildRecord`, which together are the only places a `ProducerRecord` is assembled). The single design decision behind both — "the appender passes event data through unmodified" — is deliberate and correct for the *payload*; the pattern is worth seeing as one item because a single normalisation policy at the enricher boundary addresses both findings, and because it is the only place in this codebase where untrusted data is handled at all.

Positive counter-observation (recorded for balance, not a finding): the credential-handling discipline is genuinely good and was strengthened during this codebase's recent work — the debug diagnostics were deliberately built as a diff against the operator's base properties so that credentials **cannot** appear by construction rather than by filtering, and that property is pinned by its own test. Combined with the absence of every dangerous-API class and the one-directional serialisation, the residual risk of this component is dominated by *configuration* (findings 2, 5) and *supply chain* (findings 3, 7), not by its own logic.
