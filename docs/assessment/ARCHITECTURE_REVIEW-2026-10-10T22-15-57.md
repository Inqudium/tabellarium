## 1. Executive Summary

Tabellarium's architecture still fits its problem, and the structural work since round 4 moved in the right direction: the composition root was cut into a pure `RecordPlan` and a stateful `KafkaTransport` whose reverse-ownership close order exists exactly once, the two dispatchers share one `BoundedWorkerDispatcher` skeleton that has not diverged since, restart was refused by ADR-0004 instead of being made symmetric, and the Micrometer-typed API was moved out of the appender class after a real `NoClassDefFoundError` rather than hidden behind reflection. Nothing is Critical or High. The tendency of this round is a **mild over-supply at the edges of the core**: a self-logging-guard interface plus factory whose named justifying force (a second, process-wide implementation) was since realized *inside* the single implementation, so the seam now serves three test substitutions (finding 1); a home-grown meter-mirroring registry that re-publishes the Kafka client's metrics under the appender's prefix - a naming convenience bought with a breaking rename, a listener-driven bridge and an untested generic branch, still unreleased and therefore cheap to decide (finding 2); and a metrics subsystem that has grown to 35 % of the production code (969 of 2 755 code lines, seven files) while its central orchestrator, `MetricsBindings`, has no isolated test and is proven through 21 tests inside a 4 584-line composition-root test file (finding 3). Two Low findings cover test- and benchmark-only seams in production signatures and the one-row drift between ADR-0002's surface table and the published API. The problem baseline still lacks the input every "is this proportionate?" judgment leans on: real consumer deployments, production rates and the actual use of the four topic classes remain `[MISSING - please supply]`, for the fifth round running.

**Test verdict (tests in scope):**

1. **Testability of the architecture:** very good and structurally earned - every unit below the appender is constructible without Spring, Docker or a broker; the seams are function-shaped (`ProducerFactory`, `sendAction`, injected nano clocks, `KafkaAppenderMetrics`), visibility is `internal`, there is no synchronous bypass in production code, and the lifecycle's transaction boundaries (`RecordPlan.from` before any resource, `KafkaTransport.open` with rollback) are observable at the class. The structural residue is unchanged: the drain budgets are wall-clock constants, so the shutdown proofs poll (the defect analysis's standing pattern 1).
2. **Utilization & coverage (test pyramid):** a healthy base used almost to the full - 427 test methods, 459 executions offline in ~38 s on `MockProducer` and hand-written fakes, 14 `ApplicationContextRunner` uses confined to the Spring listener (the right level for it), 3 Joran round trips, one real-broker proof in its own CI job, 3 Jazzer targets. The shape is top-heavy *inside* the offline run, though: the composition-root file holds a quarter of all tests (106 of 427), 42 % of the offline wall time (16.1 of ~38 s) and has grown by 2 541 lines since round 4 while the appender's own code shrank, because new component behaviour (metrics binding, the meter mirror, info gauges) is proven there instead of at the class that owns it - good seams, partly unused.
3. **Most significant gaps & anomalies:**
   - `MetricsBindings` (291 code lines: identity probe, bind ordering, own breaker binder, Kafka-binder probe, mirror, unbind) has no test class of its own; its 21 proofs live in `KafkaAppenderTest` and pay a full appender start/stop each (finding 3).
   - The `SelfLoggingGuard`/`SelfLoggingGuardFactory` seam is used by exactly three tests and by no production variant; the rollback test for "the guard factory throws" exists only because the seam can throw (finding 1).
   - Three production signatures carry parameters or methods whose only caller is a test or the benchmark - `queueFactory`, `startCloser`, `DeliveryOwnership.reset()` (finding 4) - against the project's own stated yardstick that "a seam only for the tests was not worth the surface".
   - The generic `else` branch of the meter mirror (meter types the Kafka binder never registers) is covered by none of its nine tests (part of finding 2).

## 2. Problem Baseline & Methodology

- **Core domain (re-verified at this commit):** a Logback appender library - encode on the caller, route by SLF4J marker (`TopicRouter`), classify into four producer-policy classes with mandatory overrides and a `max.block.ms` cap (`TopicClass`, `ProducerPropertiesBuilder`), hand off in O(1) to one bounded queue and worker per active class (`SendDispatcher` on `BoundedWorkerDispatcher`), send through a per-class breaker with half-open throttling (`ResilientMessageSender`, `HalfOpenThrottle`) under an exactly-once ownership protocol (`DeliveryOwnership`), divert what cannot be shipped into an optional fallback appender through a second bounded queue (`FallbackDispatcher`), keep the appender out of its own echo (`ClientIdSelfLoggingGuard`), account every loss, and publish metrics on demand. Code mass: 2 755 code lines in 28 files with 3 623 comment lines (ratio 1.32; `KafkaAppender` 363/482, `MetricsBindings` 291/220, `MicrometerKafkaAppenderMetrics` 308/177, the smallest units up to 4:1). The metrics subsystem (`MetricsBindings`, `MicrometerKafkaAppenderMetrics`, `KafkaAppenderMetrics`, `KafkaAppenderMetricsBinding`, `KafkaAppenderMeterRegistry`, `RenamingMeterMirror`, `AppenderInfo`) is 969 code lines, 35 % of the production code - up from ~30 % in round 4 - for an optional feature; it stays isolated behind one interface and one extension function, and its hot-path cost is measured (`./benchmarks/results/2026-10-10/`), which is why the share itself is recorded as a trend, not a finding; the one mechanism inside it without a documented force is finding 2.
- **Real requirements & scale:** the documented forces are unchanged and real - callers (incl. Reactor event loops and virtual threads) must never block, memory must stay bounded, classes must fail independently, loss must be visible, shutdown must fit a 30 s termination grace, dependencies must stay optional, a failed or reloaded configuration must leak no producer (a producer is network threads plus a 32 MB buffer). The performance analysis of 2026-08-29 *assumed* 10 k events/s; every optimization since is benchmarked before and after. **Still missing, for the fifth round running:** consumer deployments, production rates, whether FUNCTIONAL/PERFORMANCE are used anywhere, whether any operator asked for a single metric prefix or for breaker tuning. Every proportionality judgment below is therefore calibrated against the documented forces, not against observed use.
- **Team & process context:** single maintainer; the repository doubles as the reference template for the Inqudium ecosystem's build/CI/quality machinery (six workflows, 577 lines; SBOM/OSV, CodeQL, Scorecard, SLSA provenance, reproducible builds, Dokka site, Jazzer nightly, three Python generators) - a deliberate, documented investment that is not reported. The development mode is review-driven: since round 4, 84 non-Dependabot commits on nine days; on 2026-10-10 alone six defect analyses with 64 findings (0 Critical, 3 High; totals 15, 6, 12, 2, 6, 23 - not yet converging) and one code-style analysis, each followed by a fix commit. This cadence is what produced the hardening pattern in section 6.
- **Documented architectural intent:** ADR-0001 (comment prefix vocabulary; in use - 14 ADR citations in production code next to 29 citations of eleven dated review reports, each carrying the local rule as the ADR demands), ADR-0002 (public API = operator surface), ADR-0003 (Fuzz workflow is the fuzzing signal), ADR-0004 (no restart; enforced at `./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:306-317`); the README "Delivery guarantees" section; CONTRIBUTING (lock-free hot path, no synchronous test modes, no mock libraries, three-question test rationale, generated evidence); standing decisions in earlier status entries (own Resilience4j binder for its teardown lifecycle - re-verified, still load-bearing, now pinned by `CircuitBreakerMetricsMirrorTest`; the `external-contract` characterization test kept until a target repository exists - still here, with ~20 lines of profile composition in the POM; producer-registry consolidation deferred; `KafkaTransport` covered through the appender tests by the comparison report's finding 22; the half-open throttle justified analytically, comparison finding 21 still open). **Code versus ADRs:** one drift - ADR-0002's table lists four public declarations, the module now publishes five (finding 5); everything else matches.
- **Technology coherence:** sound and unchanged - blocking Kafka client behind dedicated platform-thread workers, `UnsynchronizedAppenderBase`, `LinkedBlockingQueue` hand-offs, Resilience4j 2.4, Micrometer/Spring/Logstash optional and probe-gated (Micrometer additionally kept out of every appender method signature for Joran); no coroutines, no Reactor, no persistence; the Spring Boot BOM is imported as a version universe only (the parent-POM leak of comparison finding 23 is fixed). The only Spring code is the one `@EventListener` helper.

Coverage is published from the build (~91 % in round 4; not re-measured here).

1. **The composition-root test is the default home for component proofs** - counting basis: `./src/test/kotlin/eu/inqudium/tabellarium/KafkaAppenderTest.kt` holds 106 of 427 test methods in 21 nested groups and 4 584 lines (+2 541 since round 4), among them 21 metrics-lifecycle tests for `MetricsBindings` (no own test class), 4 rollback tests for `KafkaTransport` (placed there by a recorded decision), 3 mirror tests with real producers and the info-gauge proofs; every feature added on 2026-10-10 was proven there. 2. **Hardening per review cycle at the lifecycle boundary** - counting basis: six defect analyses on 2026-10-10 with 64 findings; five `Throwable`/`Error` rollback sites in production (`./src/main/kotlin/eu/inqudium/tabellarium/KafkaTransport.kt:254`, `ProducerRegistry.kt:246`, `MicrometerKafkaAppenderMetrics.kt:470`, `KafkaAppender.kt:349` and `:373`, `ParallelClose.kt:55`); 12 test sites in 7 files that throw VM errors on purpose; 3 test-only seams (finding 4); 29 review-report citations in production comments against 14 ADR citations. Verdict: **mostly load-bearing** - a leaked producer is real (threads, 32 MB, MBeans), Logback reconfiguration cycles are real, and each branch repairs a verified defect; the margin is the VM-error symmetry (rolling back producers on an `OutOfMemoryError`, running closers inline when a closer thread cannot be created), whose benefit in a JVM that is out of memory is marginal while its cost - every future close path must answer "and on `Error`?" - is permanent. Recorded as awareness, not as a finding: no clear alternative exists short of a rule ("`Error` propagates; rollback covers `Exception`") that would itself have to be decided and written down, ideally as the fifth ADR. The design record is meanwhile tilting toward the dated reports: eleven of them are cited from code, four ADRs exist, and the last ADR is a month old while 64 findings were fixed since.
   - **Status:** Deliberately tolerated (2026-10-11). The `Throwable`/`Error` rollback sites and the VM-error test sites stay as they are - the verdict was "mostly load-bearing", and the one speculative edge (VM-error symmetry) was not worth a removal cycle of its own.
