## 1. Executive summary

No measurement artefacts were supplied; this is a **hypothesis-generating static analysis**, and under the two-axis evidence scheme that has a hard consequence stated up front: nothing here is `Effect: measured`, no retention mechanism exists that could reach P1 through the construction gate, and so **this report is a prioritized measurement list, not an optimization plan** — its single P2 finding is a measurement request, not a change request. Under the assumed load profile the appender's runtime cost is dominated by work it delegates by design (the encoder on the caller thread; `producer.send` plus compression on the per-class worker); the appender's own contribution per event is a thin envelope — guards, two map lookups, one bounded-queue hand-off, a countable convoy of small transient objects, and, when metrics are bound, the instrumentation hooks. The structural facts are performance-friendly and code-established: O(1) caller path with the queue hand-off as its only synchronization point, every buffer bounded, all expensive construction at startup, no unbounded retention anywhere, lifetime classes uniformly transient/batch/global. What remains: one hand-off mechanism whose behaviour under high fan-in only a measurement can settle (finding 1, the P2), two small established-mechanism allocation clusters worth measuring only if a host profile ever points at the appender (findings 2–3), and three items explicitly recommended to leave alone — one of them primarily a documentation bug (finding 4).

**Performance verdict:**

1. **Dominant cost:** CPU per event in the *delegated* stages (encoder ≫ appender envelope; producer/compression on the worker). Basis: complete code reading and boundary attribution — a judgment about *where* cost sits, not about magnitudes, which are unmeasured.
2. **Scaling risk:** nothing breaks by mechanism — overload degrades visibly by design (bounded queues overflow to counted `queue.full` diversions; peak heap is capped at `capacity × event-graph size × (classes + 1)`). The first *silent* cost to grow is put-lock contention on the send-queue hand-off at high caller fan-in (finding 1) — plausibly relevant only well above the assumed operating point (≥ ~10×), which is exactly what the measurement plan is for.
3. **Highest leverage:** at the assumed load, none — the honest recommendation is to run measurement M1 (allocation attribution) once against a real host and, in the likely case that the appender's share is negligible, retire findings 2–3 and close the book. If a host ever operates at ≥ 10× the profile, M2 (hand-off contention) is the one measurement that decides the only substantive open question.

## 2. Scope & methodology

Stack: pure-Kotlin Logback appender library; no Spring MVC/WebFlux, no coroutines, no own persistence — the host's threading model matters at the caller boundary only (no locks on callers beyond the queue offer; virtual-thread interaction limited to the reentry guard, finding 6). Concurrency model: one daemon worker per active topic class plus one fallback worker; hand-off via bounded `LinkedBlockingQueue`s. Serialization boundary: the injected encoder. Observability: present and opt-in (Micrometer with meters pre-resolved at bind time; per-producer Kafka client metrics; breaker meters) — the no-instrumentation finding does not apply. Evidence and load profile: metadata block; all frequencies are assumptions. Method: complete read of all 17 production files (fully known from this session's audit chain, re-verified at this commit), lifetime classification per allocation site, allocation *counting* from source (countable), CPU classes only where a known-operation basis exists — otherwise `unknown`, per the classification rules. Blind spots: encoder and Kafka client internals; real consumer load profiles; every JIT-dependent magnitude (escape analysis may eliminate some counted allocations — noted per finding where plausible).

### 🟠 P2

- [ ] 1. [`./src/main/kotlin/eu/inqudium/tabellarium/SendDispatcher.kt:137` (queue), `:226` (offer)] {P2} {Mechanism: established} {Effect: unknown} {Cost type: CPU/contention} {Lifetime: transient (queue nodes)} The multi-producer hand-off is a `LinkedBlockingQueue` put-lock — the only caller-side synchronization point, behaviour under high fan-in unmeasurable from source
  - Mechanism: every logging thread's `dispatch` acquires the queue's `putLock` (plus one node allocation per event); all callers of one topic class contend on one `ReentrantLock`. The lock's existence and its position as the sole caller-side synchronization are established from source; its contention behaviour is not.
  - Per execution: CPU class **unknown** (uncontended lock cost is a known-cheap operation, but the relevant quantity — contended cost at the host's fan-in — cannot be derived from source); allocation class **< 10 objects** (basis: one `LBQ.Node` per offer, counted in source).
  - Frequency: per event; contention scales with caller-thread count × per-class rate. Assumed 1–10 k/s, 8–64 threads.
  - Aggregate: **unknown** (effect axis unknown by definition); the mechanism is plausibly irrelevant at the assumed profile and plausibly the first silent cost at ≥ ~10×.
  - Scaling: cost is a function of two operator-controlled variables (concurrency × rate) — the class of cost this analysis flags even when the current operating point is fine.
  - Verification: measurement M2 (below) — the self-contained hand-off entry decides this finding.
  - Optimization sketch (only if M2 confirms): an MPSC queue behind the same bounded/overflow semantics; new dependency plus re-verification of the drain/close accounting — which is why measurement strictly precedes change.
  - Change risk: medium-high — the drain/overflow/close accounting is the most carefully tested part of the module.

### 🟡 P3

- [x] 2. [`./src/main/kotlin/eu/inqudium/tabellarium/ResilientMessageSender.kt:272`] {P3} {Mechanism: established} {Effect: estimated} {Cost type: allocation} {Lifetime: transient} Five `RecordHeader` wrappers are allocated per event for five constant headers
  - Mechanism: `buildRecord` loops the five pre-encoded static headers into `record.headers().add(name, valueBytes)`; each call wraps name+bytes in a new immutable `RecordHeader` although neither ever varies. The header *values* are pre-encoded once (the expensive part is already solved); only the wrappers recur.
  - Per execution: CPU class **< 100 ns** (basis: five constructor calls of a two-field object — known-cheap operation); allocation class **< 10 objects** (basis: counted in source — 5 wrappers; byte magnitude not stated, header name/value sizes are runtime values). Escape analysis is implausible here (the wrappers escape into the record's header collection).
  - Frequency: per event; assumed 1–10 k/s.
  - Aggregate: estimated **small** — a single-digit-object young-gen contribution per event at the assumed rate; nowhere near a P2 on its own.
  - Scaling: linear in event rate only.
  - Verification: measurement M1 — `RecordHeader` share in an allocation profile.
  - Optimization sketch: pre-build one shared immutable `Header` list in `MessageEnricher` and pass it to the `ProducerRecord` constructor that accepts `Iterable<Header>`; extends the documented shared-read-only-array convention by one object level.
  - Change risk: low.
  - **Status:** Fixed in `efa5916` (2026-08-30), exactly per the optimization sketch, after `BENCH_REPORT-2026-08-29T11-38-12` had moved the finding to `Effect: measured` (confirmed, 160.0 B/op): `MessageEnricher` pre-builds the five `RecordHeader` instances once (`List.copyOf`-immutable), `EnrichedRecord.headers` is now `List<Header>`, and `buildRecord` passes the shared list to the `Iterable<Header>` `ProducerRecord` constructor; the canonical read-only contract on `EnrichedRecord.headers` covers the shared wrappers. Acceptance check (bench report's decision rule, same machine/JVM): `SenderPathBenchmark` unbound dropped 272.0 → 112.0 B/op — exactly the predicted 160.0 B/op — and 94.0 → 64.1 ns/op; raw output `./benchmarks/results/2026-08-30/r2-senderpath-after-finding2.txt`.

## 6. Systemic patterns

Counting basis: source reading of `KafkaAppender.append`, `SendDispatcher.dispatch`, `ResilientMessageSender.send`. Listed as one pattern so nobody "fixes" its members individually: if measurement M1 ever attributes a meaningful allocation share to the appender, findings 2 and 3 are the two actionable members; the claim guard, `PendingSend`, and the callback lambda are load-bearing for the exactly-once and outcome contracts.

## 7. Measurement plan (hand-off to a `BENCHMARK_VERIFICATION` session)

Ordered by information gain per effort. Each entry is self-contained; results move a finding to `Effect: measured` or retire it.

- **M1 — Allocation attribution in a host application** *(verifies findings 2, 3, 6 and the systemic pattern)*
  - **Code path under measurement:** the full per-event pipeline `KafkaAppender.append` → `SendDispatcher` → `ResilientMessageSender.send` in a minimal Spring Boot (or plain-main) host that logs through a started `KafkaAppender` configured with `LogstashEncoder`, one TECHNICAL class, MDC `traceId` set, `bindMeterRegistry` called; broker may be a local container or a no-op-fast `ProducerFactory` stand-in for pure appender attribution.
  - **Tool & baseline:** async-profiler in alloc mode, 60 s window at a steady, externally driven 10 000 events/s; run twice — with and without `bindMeterRegistry` (the finding-3 delta) — plus one run with the host's logging disabled as the zero baseline.
  - **Parameters to vary:** event rate {1 k, 10 k, 50 k}/s; payload {0.5, 2} KB.
  - **Signal:** allocation share attributed to `eu.inqudium.tabellarium.*`, `org.apache.kafka.common.header.internals.RecordHeader`, `CircuitBreakerOn*Event`, `java.time.Duration`, `ThreadLocalMap$Entry`.
  - **Decision rule:** appender-attributed share ≥ ~5 % of the host's total allocation rate at 10 k/s → findings 2/3 become `Effect: measured`, re-prioritize; share < ~1–2 % → **retire findings 2 and 3** (recommendation: leave unchanged) and record the number in the follow-up report.
- **M2 — Hand-off latency and put-lock contention** *(verifies finding 1)*
  - **Code path under measurement:** `KafkaAppender.doAppend` from N concurrent caller threads into one started appender whose `ProducerFactory` returns an auto-completing in-memory producer (so the hand-off, not Kafka, is measured); the send worker running normally.
  - **Tool & baseline:** JMH throughput+sample-time benchmark of `doAppend` (baseline: 1 thread) combined with JFR `JavaMonitorEnter`/thread-park events over the same run; JMH pitfalls to respect: consume the encoder output via `Blackhole` (dead-code elimination), warm up past C2, randomize message content (constant folding), do not measure `MockProducer` internals as broker cost.
  - **Parameters to vary:** caller threads {1, 8, 32, 128}; event rate open-loop; `sendQueueCapacity` default vs. large (to separate overflow effects from lock effects).
  - **Signal:** p99 `doAppend` sample time vs. thread count; share of time in put-lock acquisition.
  - **Decision rule:** p99 flat and lock wait negligible at 32+ threads → **retire finding 1** for any realistic load (record the ceiling); measurable p99 growth attributable to the put-lock → `Effect: measured`, finding 1 becomes the module's one genuine optimization candidate.
- **M3 — CPU attribution sanity check of the verdict** *(verifies the executive verdict, no single finding)*
  - **Code path / tool:** same host as M1, async-profiler CPU mode, 60 s at 10 k events/s with a real broker container.
  - **Signal:** CPU share of encoder vs. `eu.inqudium.tabellarium.*` vs. `org.apache.kafka.clients.*` on caller and worker threads.
  - **Decision rule:** appender share below encoder share → verdict stands, close; appender share above encoder share → the verdict is refuted and H1 must be re-analyzed with the profile in hand.
- **M4 — Degraded-mode retention behaviour** *(no finding today; guards the bounded-queue claim)*
  - **Code path / tool:** M1's host with the broker stopped for 60 s under 10 k events/s; observe `kafka.appender.events.fallback` rates, both queue gauges, and GC logs.
  - **Signal / decision rule:** heap plateau consistent with the configured capacities and no old-gen promotion spike → the batch-scope claim holds; a promotion spike or unexplained growth → open a new retention finding with the dump in hand.

## 8. Examined and unremarkable

Checked and found unproblematic (deciding observation each): **regex/expensive construction** — all patterns, client ids, static header values, and meters are built once at startup or bind time; **strings on hot paths** — none outside the encoder boundary (diagnostics are startup/error-path only); **exceptions as control flow** — none; the hot-path try/catch costs nothing untaken and the error path is storm-suppressed; **boxing** — none per event (`ThreadLocal<Boolean>` uses cached constants; no nullable primitives on hot paths); **`Enum.values()`** — cached `entries` used throughout; **collection pipelines on hot paths** — none (the bind-time `associateWith` chains of finding 4 run once); **producer self-logging guard** (`./src/main/kotlin/eu/inqudium/tabellarium/KafkaAppender.kt:594`; carried over from the predecessor's addendum after re-verification) — fast path is a lazily captured, event-cached thread name plus a first-character-failing `startsWith` (CPU class < 100 ns, basis: known string-compare behaviour; no allocation); slow path (any Kafka producer network thread's log event in the JVM, including the application's own producers) allocates one transient substring for the set lookup — allocation class < 10 objects at a frequency bounded by the JVM's Kafka-client logging rate; a zero-allocation full-name-set variant exists but is not worth a second derived structure; **retention & leaks** — none anywhere: both queue types capacity-bounded, counters primitive, `MetricsBindings` holders bounded by breaker count, meters deregistered on stop (rebind cycles tested leak-free), no unbounded map/queue — which is also why the retention gate to P1 is verifiably closed; **caches** — none beyond intentional startup constants; **reflection** — none at runtime (one bind-time `Class.forName` probe); **backpressure** — bounded with counted overflow by design; peak retention `capacity × event-graph size × (classes + 1)`, operator-tunable; **reactive/coroutines/persistence** — not present; **startup** — eager producer construction and meter pre-resolution once per configuration; the per-producer buffer footprint at multiple active classes is a documented consolidation trade-off in the README's future work; **worker idle cost** — 100 ms poll timeouts, negligible; **time sources** — two reads per send, minimum for a duration (finding 5).
