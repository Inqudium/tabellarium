## 1. Executive Summary

For its actual job, tabellarium is largely cleanly decomposed: routing and property composition are pure, Kafka I/O and fallback I/O sit behind clear boundaries, and the asynchronous dispatchers answer the real requirement of not binding logging callers to broker or filesystem I/O. The complexity of the queue, breaker, and shutdown paths is therefore mostly load-bearing and not an over-engineering finding. The largest architectural deviation lies on the other side of the scale: the `AUDIT` class and "audit-grade delivery" promise a durability that the volatile, bounded in-memory queues, daemon workers, and optional/likewise lossy fallbacks fundamentally cannot guarantee. The architecture is thus coherent as an observable best-effort log transport, but under-dimensioned as a robust audit trail. At the same time, the current state shows a tendency toward over-engineering on secondary axes: a 412-line custom Resilience4j metrics binder alone replicates library behavior for a multi-appender special case, even though the standard binder already handles breaker tags. The production architecture furthermore contains two synchronous shadow modes of operation intended only for tests, which the majority of the appender tests use by default. The single-module cut, the two genuine abstraction seams (`ProducerFactory`, `KafkaAppenderMetrics`), and the optional Spring integration, by contrast, are appropriate to the size of the problem. In total, **7 findings** were identified: 0 Critical, 1 High, 3 Medium, and 3 Low; the overall tendency is a mixture of under-engineering with respect to the claimed audit level and growing hardening/observability complexity around an otherwise focused appender.

**Test verdict:**

1. **Testability of the architecture:** Good to very good. Pure core objects, injectable producer creation and clocks, and function-based dispatcher seams allow almost all domain and lifecycle rules to be verified without a Spring context, broker, or Docker.
2. **Utilization & coverage (test pyramid):** The fast base is very broad: statically counted, 263 `@Test` methods, 259 of which run in the default run; no `@SpringBootTest`, 4 lightweight `ApplicationContextRunner` usages, 3 Joran/XML tests, and dedicated dispatcher tests. The pyramid is bottom-heavy, however, with no real Kafka broker tier, and many of the 63 `KafkaAppenderTest` tests bypass both asynchronous production paths by default.
3. **Most significant gaps & anomalies:**
   - No successful wire/broker integration test for the central external system boundary (Finding 4).
   - Two test-only synchronous modes create a second execution architecture in the production code and are enabled by default by the central appender fixture (Finding 3).
   - 127 detailed test rationales and 8,601 test lines represent a high maintenance burden, but are sufficiently justified by the documented convention and the many non-trivial concurrency contracts; no separate finding is derived from this.

## 2. Problem Baseline & Methodology

- **Core domain:** A Logback appender encodes structured events, routes them to Kafka topics based on SLF4J markers, selects producer policies per topic class, enriches records, protects Kafka with circuit breakers, and optionally forwards undeliverable events to a Logback fallback. The system is a library, not a Spring service; Spring serves only the optional Micrometer binding.
- **Problem/code mass:** 17 production files with 4,806 lines and 20 test/support files with 8,601 lines. A substantial share consists of KDoc and test rationales; nevertheless, the dispatcher, metrics, and lifecycle subsystems now make up more architectural mass than routing and record preparation combined.
- **Real requirements:** Visible and plausible are a non-blocking caller path, bounded memory, independent policies per log class, detectable losses, clean shutdown, and optional dependencies. Concrete production rates, queue sizing data, load profiles, measured latency budgets, and the actual number of parallel appenders are **[MISSING - please supply]**; the documentation cites hypothetical high-load/100-service scenarios, but no measurements. The repository names one developer; the real team size and onboarding frequency are **[MISSING - please supply]**.
- **Scale and operational maturity:** The intended deployment environment is Kubernetes microservices with Kafka and optionally Prometheus/Grafana. Dashboards, detailed loss metrics, security pins, and shutdown budgets indicate high operational maturity; robust benchmarks or real deployment configurations are not present in the repository.
- **Documented architectural intent:** There is no ADR directory and neither `./CLAUDE.md` nor `./AGENTS.md`. Architectural decisions are instead documented in great detail in `./README.md`, `./docs/config/kafka-appender-config-guide.md`, `./CONTRIBUTING.md`, and KDoc. Recognized as load-bearing forces in particular were "caller never blocks", bounded queues, no broker/Docker dependency in the fast test run, optional Spring/Micrometer dependencies, and per-class isolation.
- **Technology coherence:** No reactive stack is feigned. The blocking Kafka client runs behind one worker per active class; the technical form thus matches the non-blocking goal. Spring and Micrometer are optional, and pure functions dominate routing/composition. The coherence gap lies not between Reactor and blocking, but between best-effort logging and the audit/compliance semantics.
- **Persistence/messaging topology:** There is no persistence of its own. The path is caller → bounded `SendDispatcher` queue → Kafka producer/callback → on rejection, bounded `FallbackDispatcher` queue → third-party Logback appender. Both internal handoffs are volatile; Kafka is the first durable system boundary.
- **Test topology:** 263 static `@Test` occurrences; four of them reside in an `external-contract` class that is excluded by default. The default run is unit/component-heavy, with `MockProducer`, hand-written fakes, latches, and injected clocks. Three Joran tests build the real XML surface and a real Kafka producer against an unreachable port; they verify the error/fallback path, but no successful broker round trip. A current build/coverage run was not permissible due to the pure-analysis write restriction; coverage data is missing.
- **Methodology:** First, the module, data-flow, thread, resource, and dependency boundaries were fully reconstructed. Then all relevant units were ranked, and those scoring 5 and above were checked against the problem, justifying forces, ongoing costs, and the simplest viable alternative. Earlier reports were read only after the independent reconstruction and used solely for targeted verification of current remediation/history claims.
- **Known blind spots:** No consumer repositories, actual `logback-spring.xml` files, broker configurations, incident/SLO data, or runtime metrics available. It is therefore not claimed that losses actually occur; what is assessed is which guarantee the structure can fundamentally support. The current test status is static and not confirmed by a run performed by this review.

### 🟠 High

- [x] 1. [Audit/compliance delivery — `./pom.xml:20`, `./src/main/kotlin/eu/inqudium/tabellarium/TopicClass.kt:63`, `./src/main/kotlin/eu/inqudium/tabellarium/SendDispatcher.kt:235`, `./src/main/kotlin/eu/inqudium/tabellarium/FallbackDispatcher.kt:203`, `./docs/config/kafka-appender-config-guide.md:544`] {High} {Confidence: high} {Paradigm Mismatch / Under-Engineering / Consistency} "AUDIT" and "audit-grade delivery" exceed the durability that a volatile best-effort logging path can support
  - Actual structure: `AUDIT` enforces `acks=all` and idempotence before a record reaches Kafka. In front of that, however, sits a bounded in-memory send queue; on overflow, records are diverted. The optional fallback in turn has a bounded in-memory queue, can lose records on overflow/timeout, and runs on a daemon thread. Without a fallback, records are dropped directly; on a process crash, both queues are lost.
  - Solved problem / justifying force: Not blocking request/event-loop threads and bounding memory are real, documented forces; the Kafka overrides do genuinely increase the broker-side durability of a send that has already been accepted. These forces justify the best-effort architecture, but not the repeated classification as "maximum", "compliance requirement", or "audit-grade delivery" for BaFin/MaRisk-relevant audit trails. The documentation openly names the loss paths and thereby itself confirms the limit of the guarantee.
  - Cost: Operators may confuse producer policy with end-to-end audit durability and treat a volatile logging pipeline as compliance evidence. At the same time, breaker, override, warning, and metrics complexity accrues without closing the decisive gap before the first durable store; a JVM crash, queue overflow, or aborted shutdown can still lose precisely those events classified as `AUDIT`.
  - Simpler alternative: Either explicitly name the four classes as best-effort transport/producer policies and confine every audit-grade/compliance guarantee to that narrow tier, or provide a durable local spool/outbox boundary before the asynchronous handoff for genuine audit requirements. Either is more consistent than today's mixture of hard compliance language and soft loss semantics.
  - Reversibility: A pure correction of naming and promises is cheap, but may touch consumer expectations. Genuine durability would be an expensive, hard-to-reverse architectural change with storage, recovery, and operational consequences; the actual compliance requirement must therefore be decided explicitly first.
  - **Status:** Fixed in `6d2a025` (2026-08-29), first alternative (confine the promises to the tier they can support). Product decision explicitly documented: the topic classes harden the **Kafka producer policy**; the appender remains best-effort transport with visible loss. "audit-grade delivery" was replaced in the POM description, README introduction/class table, `docs/index.md`, `docs/api-module.md`, the config guide (A.3), and the `TopicClass` KDoc; the README gained a dedicated "Delivery guarantees" section (including an outbox recommendation for hard completeness requirements), `TopicClass` a "Scope of the guarantee" paragraph, and the override warning quoted in the README/guide once again matches the actual message text ("non-negotiable topic-class requirement"). The enum name `AUDIT` is retained as public API — it still correctly denotes the producer-policy tier.

### 🟡 Medium

- [x] 2. [Metrics subsystem — `./src/main/kotlin/eu/inqudium/tabellarium/MetricsBindings.kt:23`, `./src/main/kotlin/eu/inqudium/tabellarium/MetricsBindings.kt:95`, `./src/main/kotlin/eu/inqudium/tabellarium/MetricsBindings.kt:241`, `./pom.xml:170`] {Medium} {Confidence: high} {Over-Engineering / Dependency & Build Appropriateness} A custom Resilience4j Micrometer binder replicates library behavior for an unsubstantiated multi-appender special case
  - Actual structure: `MetricsBindings` comprises 412 lines and registers the complete standard meter family manually, holds volatile timer/counter sinks via an `IdentityHashMap`, attaches non-removable event consumers to breakers, and implements its own rebind/teardown. Together, the four metrics classes comprise 1,171 lines (about 24% of the production lines). The stated justification is an `appender` tag so that two identically named breakers from different appenders do not collide in the same `MeterRegistry`.
  - Solved problem / justifying force: Multiple appenders in one registry are technically possible, lifecycle-symmetric deregistration is real, and unique meter IDs are required. What is missing, however, is a substantiated multi-appender use case or a measurement justifying the local re-implementation of the complete Resilience4j metric semantics. The locally inspected Resilience4j 2.4.0 standard binder already carries over tags of the `CircuitBreaker`; the required appender dimension is therefore not a fundamentally missing library feature.
  - Cost: Every Resilience4j upgrade must be checked for new/changed meters, states, tags, and event semantics and mirrored locally. The non-removable consumer lifecycle forces additional holder/volatile logic and several appender-level tests; onboarding leads through a second metrics implementation before the actual log delivery becomes visible.
  - Simpler alternative: Tag breakers with the appender tag at creation time and optionally use the maintained `TaggedCircuitBreakerMetrics` binder; alternatively, publish only the already existing appender-specific delivery/queue metrics if there is no real need for the complete Resilience4j series.
  - Reversibility: moderate. Metric names and dashboards can remain stable, but bind/unbind behavior, the optional dependency, and the multi-appender tests must be converted together. The isolated `MetricsBindings` cut limits the risk.
  - **Status:** Deliberately not restructured; rationale corrected in `6d2a025` (2026-08-29). Evaluation of the alternative showed: `TaggedCircuitBreakerMetrics` does propagate breaker tags (so the uniqueness part of the previous KDoc rationale was incomplete), but offers **no teardown API** — meters are removed only when a breaker is removed from an observed `CircuitBreakerRegistry`. The symmetric `unbind()` on Logback reconfiguration/stop is a real, tested requirement (meter-leak tests); with the standard binder, the same removal logic would have to be rebuilt locally, eliminating the hoped-for simplification. The `MetricsBindings` KDoc now states the accurate rationale (lifecycle rather than tag capability) and explicitly names the accepted ongoing costs (checking Resilience4j upgrades against the mirror).

## 6. Systemic Patterns

1. **Compliance language sits one tier above the actually durable boundary** — Finding 1 is not an isolated text error but runs through at least **6 surfaces** (POM description, README introduction/class table, docs index, config guide, `TopicClass`, startup warnings) and meets **2 volatile queue boundaries** plus several explicit drop paths. Counting basis: search for `audit-grade`, `AUDIT`, `compliance`, `drop` and complete tracing from append to fallback. A single explicit product-decision document — best effort with a narrow producer policy, or a genuinely durable audit trail — would realign naming, documentation, and architecture.

2. **Synchronous shadow paths for test convenience** — **2 appender hooks** and **2 dispatcher switches** in **3 production classes**, jointly enabled by default in the central fixture; a total of **16 test references** to these modes, with only seven explicit switches back to asynchronous. Counting basis: `useSynchronousSendForTests`, `useSynchronousFallbackForTests`, and `synchronous = true/false` under `./src/test/kotlin/`. The finding is systemic because it affects not a single assertion but the execution model of the appender test layer.

3. **Rationale drift after the introduction of the SendDispatcher** — at least **3 authoritative documentation locations in 3 files** still describe the earlier caller-thread path, while the code and another README section describe the worker handoff correctly. Counting basis: complete search for `max.block`, `caller`, `reactive` and cross-checking of the current control flow. The drift is small in fix effort, but a signal that the very dense KDoc/README mass is not updated atomically on architectural changes.

**Positive counter-patterns (no findings):** The optional dependencies are consistently encapsulated, active rather than hypothetical topic classes determine resources, all queues are bounded, and the production logic offers genuinely isolable seams instead of blanket single-implementation interfaces. There is no CQRS/DDD/microservice theater, no reactive paradigm mix, and no unnecessary controller-service-repository layering.
